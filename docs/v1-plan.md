# HeyAgent v1 开发方案（草案，待你确认）

> 2026-10-17 · 依据：定稿原型 v3.2（`design/`，说明见 `design/README.md`）和 4 份技术调研（`docs/research/` 下的 `agent-runtime.md`、`backend-stack.md`、`browser-stack-2026-10.md`、`platforms-v1.md`）。
> 这份方案只定「做什么、怎么搭、用什么」，还没有写任何产品代码。你确认后再开工。

## 0. 一页纸结论

- **v1 做的是通用平台，搜品是用它配出来的第一个业务。** 产品代码里只有通用能力：任务和 session、工具（HTTP 接口、MCP、浏览器）、技能、记忆、规则、检查点、三方验收、待办。搜品要的东西都写在技能、记忆、规则和工具配置里，由主管在控制台里配，不写进代码，包括去哪些网站、怎么以图搜、怎么分辨工厂、客户偏好、比价表的格式。换一个岗位，只换配置（见 2.0）。
- **第一个业务：搜品。** 搜品岗贴一个客户的商品链接，agent 解析商品，去亚马逊、Temu 看同款售价，去 1688 以图搜找工厂，按记忆筛选，产出一张比价表交负责人审核，最后由另一家的 AI 逐条验收。**询价、下单付款、给客户发消息 v1 都还由人做**，agent 只起草和整理。验收时再用同一个平台配一个别的岗位的业务，证明不改代码也能用。
- **怎么搭：session 引擎自己写，其余用成熟的库。**
  - 「挂起几天后在原 session 继续」「每一步落库并实时显示」「规则由程序执行、模型绕不过」这三件事，现成框架都做不到；按我们的规模，自己写不难。
  - 调模型用 Vercel AI SDK 7，OpenRouter 和 Ollama 都能接。
  - 业务数据、任务队列、挂起等待都放在一个 PostgreSQL 里，不另上工作流引擎和 Redis。
  - 浏览器：服务器上跑有界面的 Chrome，agent 通过 Playwright MCP 操作；登录态加密存在保险箱里；人在控制台里看远程画面登录、过验证码。这套做法的主链路已经在开发机上试跑通。
- **用什么：TypeScript 全栈。** 前端由定稿原型直接改造；后端 Hono + tRPC，PostgreSQL 18 + Drizzle + pg-boss，better-auth 登录；用 Podman 跑 4 个容器（不用 Docker）。版本都核对过（第 3 节）。
- **工期：约 9 周开发 + 2 周试点**，按 1 名全职工程师配合 Claude Code 估算。分 5 个里程碑，每个结束时演示一次。第 1 周先实测风险最高的三件事：远程画面好不好用、真实代理能不能转发、各平台的登录能不能保持（第 4 节）。
- **要花的钱：** 模型费用（目标每个请求平均不超过 1 美元）；一台内网服务器（同时跑 5 个 session 约 8 核 16GB）；美国出口代理；第三方数据服务可选。
- **最大的风险是平台风控和条款**，其次是网页里的提示词注入和花费失控（第 5 节）。对策：专用账号、人工登录、低频访问、遇到验证码转人工；对外动作一律审批；1688 同时申请官方接口。
- **6.1 的 6 件事你已经定了**（2026-10-17）。还要你定的在 6.2：M1 一开工就要用到第 15 条（表单库和 Markdown 显示）和第 16 条（OpenRouter 的 key）；第二个业务已定为物流运单跟踪（第 17 条）。另有 3 件慢事建议现在就启动：1688 开放平台企业申请、Meta 商业验证、为 agent 准备专用账号和代理。

## 1. 目标和范围

### 1.1 v1 要跑通的业务（全部用配置搭）

下面两个业务都**不写专用代码**：
- 步骤、检查点、目标写在任务里；
- 去哪些网站、怎么操作写在技能里；
- 客户偏好写在记忆里；
- 要调的接口配成 HTTP 或 MCP 工具。

平台缺什么，就补任何岗位都能用的通用能力（见 2.0）。

**主场景：搜品。** 搜品岗把客户发来的商品链接交给 agent，agent 依次：

1. 解析商品（标题、主图、售价、规格）；
2. 去亚马逊、Temu 看同款和售价；
3. 去 1688 以图搜同款、找工厂；
4. 按选中的记忆筛选（例如「Nova Home 只要工厂，单价 3 美元以内」）；
5. 整理成比价表，交负责人审核（这一步可以挂起等人）；
6. 审核通过后，三方 AI 验收检查点；AM 拿比价表去回客户（v1 由人发 WhatsApp）。

**第二个场景：物流运单跟踪，验证通用**（2026-10-17 你定的）。「每天 09:00 打开承运商的查询页，查一批运单的状态，把延误的整理成清单提醒负责人」。
- 它和搜品不共用任何技能和工具配置，用来证明换业务不用改代码；
- 同时验证 cron、每次触发一个新 session、遇到验证码挂起等人，以及读附件、存文件、通知这几个通用能力；
- 也全部是配置：运单清单 v1 由物流同事用表格附件更新到任务上，以后可以配一个 MCP 工具接公司 ERP；查哪些承运商、怎么算延误，写在技能里。

两个场景合起来，会用到原型里的全部核心机制：步骤和检查点、规则拦截、挂起等人后继续同一个 session、三方验收、记忆和技能、浏览器保险箱、按账号并发、待办看板。

**试点验收标准（建议，试点 2 周）：**

| 指标 | 目标 |
|---|---|
| 20 个真实搜品请求里，负责人直接通过或小改后通过的比价表 | ≥ 70% |
| 每个请求占用的人工时间 | 比现在少一半以上（开工前先量一下现在要多久） |
| 每个请求的模型花费 | 平均 ≤ 1 美元 |
| 越权 | 0 次：没有任何未经审批的对外动作 |

### 1.2 v1 包含的功能（对照原型页面）

| 原型页面 | v1 做到什么程度 |
|---|---|
| 任务 | 全做：新建（任务、可选步骤带「等待」「检查点」、目标、用哪些、模型、定时）、卡片墙、抽屉详情、启用和停用、立即运行。新建和立即运行时可以带附件（图片、文件） |
| Session | 全做：全部 session 列表、过程（检查点、工具调用的输入输出、token、花费、验收）实时刷新。agent 产出的文件（表格、文档、截图）在过程里能直接看、能下载 |
| 待办 | 全做：五列看板；要人办的事（审批、验证码和登录、验收争议、记忆和技能审核）；人加的待办（定时、cron、等事件带兜底、先到先继续） |
| 记忆 | 全做：新建、「适用于」可新建、agent 提议后人审核 |
| 技能 | 全做：SKILL.md 编辑、agent 提议的修改由人审核 |
| 规则 | 做：原型里那 9 条规则作为示例配置灌进去（是数据，不是代码）；新建规则时，系统把「触发条件」翻译成程序能判断的条件，给人确认（见 2.3.2） |
| 工具 | 全做：HTTP 接口（cURL 导入、密钥 `{{名字}}`）、MCP 服务器、内置工具 |
| 浏览器 | 全做：多个 Chrome、代理、远程画面登录、登录态保险箱、按账号并发。原型要加几个字段（见 2.3.6） |
| 模型 | 全做：OpenRouter + Ollama、各角色默认模型、验收不许同一家。Ollama 要等有显卡的机器（见 2.3.4） |
| 看懂架构 | 最后再搬：原型页面直接搬过来，改成读真实数据 |
| 用户和权限 | 做最简单的：账号密码登录，主管和员工两种角色，员工能看全部、只能操作自己的 |
| 通知 | 站内（侧边栏数字）；外部渠道待你定（见第 6 节） |

### 1.3 v1 不做的（以及什么时候做）

| 不做 | 原因 | 计划 |
|---|---|---|
| 自动下单付款 | 涉及钱，先让搜品跑稳 | v1.1 采购：1688 下单 + 规则「下单前必须主管审批」 |
| 自动给客户发 WhatsApp | 要用官方 Cloud API，得先办 Meta 商业验证；个人号网页版自动化会被封号，AM 的号码不能拿来试 | v1.1 AM：规则「发消息前由 AM 确认」。商业验证建议现在就办 |
| 在 1688 旺旺上自动问工厂、等回复 | 1688 没有给买家的旺旺收发接口，官方文档写明旺旺相关能力「不允许自动化批量操作」；用浏览器硬做会封号 | v1 可以让 agent 起草问题清单（长宽高、重量、起订量、打样价），人在旺旺里发，再把回复贴回来，session 挂起等人。正规通道要看 1688 询价单接口、UTP 协议和 Accio 的进展（见第 6 节） |
| TikTok Shop 自动化 | 美国站条款明文禁止自动化抓取，也没有给买家用的接口 | 不做。需要时由人用 Kalodata、FastMoss 这类工具查 |
| 物流估价 | 优先级靠后 | v1.2 |
| 桌面软件自动化 | 现在的业务流程里还没有非它不可的软件 | 有具体软件时再加；**你最早的定义里提过 v1 要能操作桌面软件，需要你确认可以推迟** |
| 规划 agent 拆给多个子 agent 并行 | v1 一个 agent 按顺序搜也够用 | v1.1；v1 的数据结构先留好「父 session」字段 |
| 记忆的向量检索 | 记忆是建任务时手选的，用不到 | 记忆多到选不过来时再加 |

### 1.4 搜品要用到的平台知识（写进技能和工具配置，不写进代码）

详见 `docs/research/platforms-v1.md`。下表是给主管写搜品技能、配工具时用的参考：每一条最后都落成一份技能（SKILL.md）、一条 HTTP 工具配置或一个浏览器配置，**产品代码里不出现这些平台**。

原则：有官方接口就配成 HTTP 工具，没有就让 agent 用通用浏览器低频访问；遇到验证码、登录失效就转人工，不想办法绕过风控。

| 环节 | v1 做法 | 说明 |
|---|---|---|
| 解析客户链接（Shopify 独立站） | 配一条 HTTP 工具，调 Shopify 官方公开的商品接口（`/products/{handle}.js`）；技能里写明：不行就读页面里的结构化数据，再不行用浏览器截图让模型读 | 从服务器 IP 请求可能被限流，要走代理、控制频率 |
| 亚马逊美国站 | 浏览器，不登录，固定一个美国收货邮编，低频访问 | 官方接口我们够不着：旧的 PA-API 已经停用，接替它的 Creators API 要求近 30 天有 10 笔联盟成交。浏览器被封时可以临时改用第三方数据服务 Rainforest（$15/月起） |
| Temu 美国站 | 浏览器 + 美国代理，进站先确认是美国站、美元价 | 反爬很强，定位为「尽力而为」，查不到直接转人工 |
| 1688 以图搜、关键词搜、筛工厂 | 浏览器 + agent 专用的买家账号（人工登录一次）；看「超级工厂、实力商家、源头工厂」这些标识区分工厂和贸易商 | 同时以公司名义申请 1688 开放平台的「跨境综合解决方案（自用）」，里面有多语言图搜接口，批下来就把浏览器换成接口。申请条件和费用目前只有二手资料 |
| TikTok Shop | 不做自动化 | 见 1.3 |
| 1688 旺旺询价、下单付款、WhatsApp | 人做 | 见 1.3 |

## 2. 架构

### 2.0 原则：平台通用，业务是配置

产品代码里**不写任何业务**：不出现岗位、平台名、比价表这类东西，也不为某个网站写专用代码。业务需要的东西，全部对应到平台上的配置：

| 搜品需要的 | 在平台上是 |
|---|---|
| 流程、要达到的结果、检查点 | 任务：步骤、目标、检查点 |
| 去哪些网站、怎么以图搜、怎么分辨工厂和贸易商 | 技能（SKILL.md），主管在技能页写 |
| 「Nova Home 只要工厂，单价 3 美元以内」 | 记忆 |
| 解析 Shopify 商品 | HTTP 工具，用 cURL 导入 |
| 公司 ERP 里的供应商库 | MCP 工具 |
| 亚马逊、1688 的账号、代理、并发上限 | 浏览器配置 |
| 比价表 | agent 用通用的「存文件」工具产出的表格 |
| 下单前要主管批、发消息前要 AM 确认 | 规则 |

代码里只有通用的东西：
- **内置工具**：读技能、提议记忆和技能修改、勾检查点、挂起等待、问人、通知；再加两个原型里没有的：
  - **存文件**：产出表格、文档，产物在 session 里能看、能下载；
  - **读附件**：读任务带的图片和文件。
- **通用浏览器**：对任何网站都一样，还能把 session 里的文件传到网页上，以图搜同款就靠它。
- **其他**：通用的 HTTP、MCP 接入；任务、session、规则、检查点、验收、待办、模型。

平台缺能力时，只补任何岗位都能用的通用能力，并在里程碑汇报里列出来。种子里的搜品数据只是示例配置，不是代码的一部分。

### 2.1 组件

```text
员工的浏览器：Web 控制台（由原型改造，React + shadcn 预设不变）
  │ HTTP（v1 先不上 HTTPS），经反向代理 Caddy
  ▼
API 服务（Hono + tRPC）
  ├─ 页面数据和操作，权限在这里检查
  ├─ 实时推送（SSE）：session 过程、看板、侧边栏数字
  ├─ webhook 入口：外部事件叫醒挂起的 session
  └─ 远程画面中转：控制台 ⇄ worker 里的 Chrome
  │
  ├── PostgreSQL：业务数据、任务队列（pg-boss）、等待表、账号租约、加密的保险箱和密钥
  └── 文件卷：截图、比价表等产物
  │
Worker（可以开多个，每个都带 Chrome）
  ├─ session 引擎：agent 循环 → 工具网关（调用前规则 → 执行 → 调用后规则 → 落库）
  │    └─ 模型层（AI SDK 7）：OpenRouter；Ollama 等有显卡的机器再接
  ├─ 规则：运行开始、调工具前、调工具后、说做完了 4 个阶段
  ├─ 工具：内置 / HTTP 接口 / MCP 客户端（公司 ERP 等）
  ├─ 检查点同步 + 三方验收
  ├─ 调度：到点叫醒、等事件、兜底提醒、cron、按账号并发、花费上限
  └─ 浏览器管理：虚拟屏（Xvfb）+ 有界面 Chrome + Playwright MCP + 代理转发（gost）
```

- API 和 worker 是同一份代码，部署成两个容器；worker 的镜像里多装了 Chrome 和虚拟屏。
- 两者之间除了远程画面要直连，其余都通过 PostgreSQL 协作（任务队列和 LISTEN/NOTIFY），所以任何一个重启都不丢状态。
- Chrome 放在 worker 里，是因为 Playwright MCP 以本机进程的方式连 Chrome，Chrome 的调试端口只开在本机。

### 2.2 一次运行的生命周期

1. **触发**：有 4 种来源：人点「创建并启动 / 立即运行」、cron、人加的待办到点、外部事件。触发后创建 session（状态「执行中」），排进队列。
2. **开始**：worker 领到 session，拼好上下文：
   - 任务、目标、步骤、检查点清单；
   - 选中的记忆；
   - 技能目录（只有名字和一句话）；
   - 工具说明（选的 + 每个任务自带的 3 个）。

   然后执行「运行开始」阶段的规则。
3. **循环**：调模型 → 模型要调工具 → 「调工具前」规则（放行、拦下、挂起等人）→ 执行工具 → 「调工具后」规则（同步检查点、截图）→ 回到调模型。每一步都落库，并推送到前端。
4. **挂起**：触发挂起的有 3 种情况：agent 调 `session.wait` 或 `ask.human`、规则要求等人、遇到验证码。挂起时：
   - 记下在等什么、什么时候继续、兜底期限；
   - 把这次浏览器里有变化的登录态合并回保险箱，关掉 Chrome；
   - 释放 worker；
   - 状态变成「挂起等待」或「等人处理」，待办看板上出现对应的卡片。
5. **继续**：触发继续的有 3 种情况：到点、来事件（人处理完、外部消息）、人点「立即继续」。session 重新排队；worker 从库里读回完整的消息历史，追加一条「等到了什么」，接着循环。**同一个 session id，前面的上下文和检查点都还在。**
6. **说做完了**：「三方 AI 验收」规则把目标、检查点和证据交给另一家的模型逐条核对，结果有 3 种：
   - 全部通过 → 已完成；
   - 有疑问 → 反问执行 agent，最多 N 轮；
   - 还是说不清 → 待办里出现「验收争议」，由负责人决定。
7. **结束**：状态变成「已完成」或「失败」，汇总 token 和花费。

### 2.3 关键设计决定

#### 2.3.1 agent 循环自己写，模型层用现成的库

详见 `docs/research/agent-runtime.md`。结论是自己写 **session 引擎**，包括 agent 循环、每步落库、规则闸门；跟模型打交道的部分用 Vercel AI SDK 7。

- **为什么自己写**：我们最难的三条要求，现成框架都不能直接满足，最后都要自己写：
  - 挂起几天后在原 session 上继续；
  - 每一步落库并实时显示；
  - 规则在固定阶段由程序执行。

  在我们的规模下这并不难：每次调模型、每次调工具都先落库；挂起就是写一条等待记录然后退出循环；继续就是从库里读回消息接着跑。
- **工具网关**：给模型的工具定义里不带执行函数，所以模型提出调用后，循环就停在那里，交给我们的工具网关。网关依次做：调工具前的规则 → 执行工具（内置 / HTTP / MCP）→ 调工具后的规则 → 落库。模型没有任何绕过的路径。
- **模型层**：
  - 云端用 OpenRouter 官方 provider，内网用 Ollama provider，MCP 用 AI SDK 自带的客户端。
  - 外面再包一层很薄的「模型接口」，并锁定版本。某个模型在 AI SDK 下出问题时，可以直接走 OpenAI 兼容接口兜底。
- **没选的方案**：
  - **Claude Agent SDK**：它的 hooks 设计最贴近我们的规则，但只能跑 Claude。它的 session 存在自己的文件里，只能镜像到我们的库。以后可以作为「Claude 专用执行器」接进来，不适合当底座。
  - **Mastra、LangGraph 等框架**：会把我们的 session、事件、规则套进它们自己的结构，而规则、检查点、验收仍然要自己写。
  - **Hermes Agent**：Python 写的单用户个人 agent，不适合 fork，但它的技能和上下文压缩设计可以借鉴。
  - **Anthropic 的 Managed Agents**：只跑 Claude，循环在 Anthropic 云上，碰不到我们内网的 ERP 和浏览器。
- **两个落地细节**：
  - 通过 OpenRouter 用 Claude 时要开 prompt caching（长 session 能省很多钱），花费按 OpenRouter 返回的 `usage.cost` 记账。
  - Claude 5.5 不接受 `temperature` 参数，代码里不要传。

#### 2.3.2 规则：用自然语言写，由程序执行

原型里规则只有「名称 + 触发条件（一句话）+ 命中后怎么办 + 会调用的工具」。但「模型绕不过」要求触发条件由程序判断，不能每次让模型理解那句话。做法：

- 保存规则时，系统用规划模型把触发条件翻译成**一种触发类型 + 参数**，显示「系统理解为：调用 whatsapp.send 之前」，人确认后才保存。原型的规则编辑器要加这一行，改动很小。
- v1 支持的触发类型：
  - 调用某个工具之前；
  - 调用某个工具之后；
  - 打开的网址不在白名单；
  - 页面上出现验证码或登录页（先按网址、iframe 和关键词判断，拿不准时把截图交给视觉模型，见 2.3.6）；
  - 花费超过 X；
  - agent 说做完了；
  - agent 提议记忆或修改技能。

  翻译不进去的，提示「这条规则 v1 还不支持」，不会偷偷变成模型自己判断。
- 运行时只按翻译结果执行。命中后的动作也是程序做：拦下、挂起等人、截图、通知、交给验收。

#### 2.3.3 检查点

- 建任务时，从每条检查点的文字认出类型和目标数，例如「访问 3 个平台」→ 访问 · 目标 3。类型有 6 种：访问、发送消息、数量达标、产出文件、人工确认、说明。原型已有规则写法，认不出来的交给模型兜底。
- agent 用 `checkpoint.mark` 打勾或跳过，跳过必须写理由。
- 「同步检查点」规则在调工具后，按工具类型自动写记录，标「自动」，agent 改不了：
  - 打开网页 → 访问记录；
  - 发出消息 → 消息原文；
  - 保存文件 → 链接。

#### 2.3.4 三方验收

- **输入**：目标、检查点和每条的记录、证据（截图、产物链接）、agent 的跳过理由。
- **输出**：结构化结果。每条检查点给出通过、不通过或存疑，并附理由。
- **执行和验收不许同一家族**：保存默认模型时、建任务时都校验，原型已经做了。
- **验收用哪个模型，要先定硬件**。原型假设内网有一台 Ollama（qwen3:32b 等），但 192.168.31.100 其实是这台开发机，上面没有 Ollama。两条路：
  - **A. 准备一台带显卡的机器跑 Ollama**：qwen3:32b 量化后大约要 24GB 显存级别的显卡（估算，买之前实测）。验收不花钱，数据不出内网。
  - **B. v1 先用 OpenRouter 上另一家的模型验收**，例如 Qwen 或 Gemini 系列：不用买硬件，但每次验收要花钱，数据也会出境。

  我建议 v1 先走 B，试点跑通以后再决定要不要上 A。试点时都要抽查验收模型的判断质量。
- **验收模型可能看不了图**：走 A 路线时，qwen3 不能看图；qwen2.5-vl 能看图，但不能调工具。所以截图类证据要先交给能看图的模型转成文字，再交给验收模型，或者直接交给人看。走 B 路线可以直接选能看图的模型（例如 Gemini），没有这个问题。

#### 2.3.5 挂起和继续

- session 的完整消息历史存在库里。继续时读回来，接着调模型，不依赖任何进程内存，服务重启也不丢。
- 长 session 要压缩上下文：较早的大块工具输出（网页快照、截图）换成摘要加存档链接，检查点和关键结论保留原文。
- **调度不上单独的工作流引擎**，用 Postgres 里的任务队列 pg-boss，再加我们自己的「等待表」（详见 `docs/research/backend-stack.md` §3）：
  - **挂起**：在同一个数据库事务里做三件事，要么一起成功、要么一起回滚：
    - 把 session 标成挂起；
    - 写一条等待记录：在等什么、到点时间、兜底期限；
    - 排一个「到点叫醒」或「到期提醒」的延迟任务。
  - **继续**：到点、外部事件（webhook 进来按条件匹配等待记录）、人处理完、人点「立即继续」，四种来源都走同一个入口。入口用「只有状态还是等待中才能改」的条件更新，谁先到谁生效，「先到先继续」自然成立。
  - **兜底期限**：到期只提醒负责人，不自动继续。
  - **定时任务**：cron 用 pg-boss 自带的定时（时区 Asia/Shanghai）。
  - **账号并发**：自建「账号租约表」，拿不到租约就挂起排队，有人释放时叫醒最早的那个。
  - **一个限制**：pg-boss 单个任务最长 24 小时，所以 agent 循环每跑一段就要落库、续租或主动挂起。我们本来每一步都落库，影响不大。

#### 2.3.6 浏览器

详见 `docs/research/browser-stack-2026-10.md`。下面这条主链路已经在开发机上试跑通：起 Chrome、装登录态、agent 通过 MCP 操作、出远程画面、网站中途换了 cookie、合并写回保险箱、关闭清理。开发机没有虚拟屏，试跑时用无界面模式代替。

M0 又在容器里用有界面 Chrome + 虚拟屏实测了一遍（`docs/research/m0-browser-spike.md`），结论成立：sandbox 在 rootless Podman 的默认配置下就能开，只需保留 SYS_CHROOT 一项权限；UA 和 `navigator.webdriver` 都正常；中文网页显示正常。修正和新发现写在下面各条里。

- **Chrome 我们自己起**：每个 session 临时起一个 Google Chrome 正式版，有界面，跑在服务器的虚拟屏里；时区、语言、窗口尺寸按配置固定；调试端口只开在本机；用完删掉临时目录。
  - 不用无界面模式，是因为实测新版无界面 Chrome 的 UA 里仍带 `HeadlessChrome`，`navigator.webdriver` 也是 true，网站一眼就能认出来。
- **两条连接，agent 拿不到完整的登录态**：
  - 编排器自己连一条（CDP），负责装登录态、导出登录态、远程画面、验证码截图；
  - agent 另连一条，用 Playwright MCP（版本锁定 0.0.83）操作页面。两条连的是同一个 Chrome，agent 用的就是装好的登录态，但它手里没有导出 cookie 的工具。
  - MCP 里在页面上执行脚本的工具（`browser_evaluate`）能读到页面脚本看得见的那部分 cookie 和 localStorage，所以按任务开放，并记审计日志。
- **登录态保险箱**：每个 Chrome 配置一份加密的登录态（cookie + localStorage，个别网站再加 IndexedDB），带版本号。
  - session 开始时装进 Chrome。
  - 结束时先打开一个探测网址，确认还在登录状态，通过了才写回，而且只写本 session 改过的项（三方合并）；版本号冲突就重读重试。
  - 探测没通过就不写回，把这个账号标成「需要人工」。
- **代理**：Chrome 和 Playwright 都不支持带用户名密码的 SOCKS5（实测直接报错）。所以每个 Chrome 配置在本机常驻一个 gost 转发进程：Chrome 连本机无密码的端口，gost 再带密码连上游代理。
  - 实测域名交给代理去解析，本地不会泄漏 DNS；另加防 DNS 和 WebRTC 泄漏的启动参数，上线前用检测页验证。
  - 代理挂了就报错、告警，**不会自动改成直连**。
- **并发**：按「平台 × 账号」发租约，默认上限 1，满了排队，session 显示「等待浏览器」。同一账号多个 session 同时用会互相顶掉 cookie，所以先保守设 1。
- **远程画面**：控制台里直接显示 Chrome 的页面画面（CDP screencast），把人的鼠标、键盘转发过去。中文输入和粘贴实测可以直接上屏。走控制台自己的登录，不用另开端口。
  - M0 实测：点击、键盘、中文输入、拖滑块、新标签页、各种弹框都能处理；本机延迟约 31～37 毫秒。2026-10-17 你在内网亲手试过，手感够用。
  - 代价比原来估的大：文字多的页面每路画面约 6～12Mbps、多占约 1 核。所以只在有人看的时候开，画面缩到 960 宽。
  - 短板：看不到地址栏和浏览器原生弹框。不够用的话，管理员有 noVNC 兜底，v2 换成 kernel-images（开源的 WebRTC 远程桌面）。
- **M2 要处理的新发现**：
  - 编排器的连接要自己处理弹框监听，否则 agent 处理弹框的工具会失效。
  - 隐藏自动化标记的那个参数，会让第一个标签页顶上多一条提示条，页面高度少 56 像素；做法是开一个新标签页、关掉第一个。
  - Chrome 自己的后台请求会经代理连十几个 Google 地址，要关掉，省代理流量。
  - 容器里没有 WebGL，这是服务器环境的一个特征。要不要处理，M2 结合平台风控来看。
- **验证码**：只检测，不破解（破解违反平台条款，也不可靠）。
  - 每次调完浏览器工具，先按网址、iframe 域名、关键词判断；拿不准时把截图交给视觉模型判断「是不是验证码页」。
  - 命中就截图、挂起 session、通知负责人。人在远程画面里处理完，点继续，回到同一个 session。
  - 视觉模型：走 2.3.4 的 B 路线时用 OpenRouter 上便宜的视觉模型，有显卡后换成内网的 qwen2.5-vl。准确率要攒几十张样本自己测。
- **省 token**：长页面的全量快照实测有 73 万字符，约 18 万 token。提示词要求 agent 先看浅层结构，再展开局部或按文字查找，不拿全量快照。截图默认只存档留证，需要时才给模型看。
- **安全**：
  - Playwright MCP 默认带一个能执行任意代码的工具（`browser_run_code_unsafe`，能拿到全部 cookie），而且没有开关能关掉，我们在工具网关里屏蔽它。
  - MCP 自带的网址限制，官方说明「不是安全边界」。网址白名单由我们自己在调工具前检查，并在浏览器层拦截不在白名单里的请求（M2 实测）。
- **资源**：每个 session 按 1～1.5GB 内存、高峰约 1 核估算。同时跑 5 个 session 约要 8 核 16GB，10 个约要 16 核 32GB。
  - M0 实测：同时开 5 个有界面 Chrome，共占 1.9GB 内存，加载时 1.8～2.6 核，空闲时不到 0.7 核；每个 Playwright MCP 另占约 115MB。按这个看，8 核 16GB 跑 5 个 session 够用，余量留给电商页面和远程画面。
- **原型浏览器页要加的字段**：出口所在地、时区、语言、登录探测网址、是否保存 IndexedDB。

#### 2.3.7 安全

- **密钥**：HTTP 工具的密钥和浏览器登录态都加密存放。模型只看到 `{{名字}}`，执行请求时才替换成真值。页面上也不显示原文。
- **网页内容不可信**：网页里可能藏着写给 AI 的指令。原型里的 m-009 就是例子：店铺页面写着「亚马逊官方认证工厂」，还夹带了一句给 AI 的话。对策：
  - 新记忆必须人审；
  - 对外动作（发消息、下单）必须审批；
  - 工具调用都受规则约束；
  - 模型看不到任何密钥；浏览器里的 agent 拿不到完整的 cookie，也执行不了任意代码（见 2.3.6）。
- **审计**：所有模型调用和工具调用都落库，谁批准了什么也落库。
- **数据出境**：发给 OpenRouter 的内容（客户名、商品、报价、网页截图）会出境，需要你知情并同意（见第 6 节）。特别敏感的任务要全程用内网模型，前提是有显卡机器（2.3.4 的 A 路线）。

### 2.5 部署：全部跑在 Podman 里

除了 OpenRouter 这个外部服务，所有组件都跑在 rootless Podman 容器里。服务器上只装 Podman，不单独装 Node、PostgreSQL、Chrome。

```text
正式服务器（Ubuntu 24.04 + Podman 4.9，普通用户运行，不用 root）
└─ systemd（Quadlet）：开机自启，挂了自动重启
   └─ pod「heyagent」，用一份 Kubernetes 格式的 YAML 描述
      ├─ web：Caddy，提供页面、转发 /api（v1 用 HTTP）
      ├─ api：Hono + tRPC
      ├─ worker：agent 引擎 + Chrome + 虚拟屏 + gost + Playwright MCP（M1 起加）
      └─ postgres：PostgreSQL 18
   卷：数据库数据，以及截图、产物等文件
   Podman secret：主密钥
   systemd 定时器：每天备份
```

- **开发机和服务器用同一套**：镜像都用 `podman build` 构建，pod 都用同一份 YAML 起。开发机上的 Podman 是 3.4.4，用脚本 `scripts/pod.sh` 直接起，包 3 正在做；服务器上再交给 Quadlet 管理。
- **更新**：v1 不搭镜像仓库。服务器上一个脚本做完全部步骤：拉代码 → 构建镜像 → 重启 pod。api 启动时自动执行数据库迁移。上一版镜像保留，出问题可以退回。
- **备份**：每天 `pg_dump` 一次，连同文件卷一起复制到另一块盘或 NAS，保留 14 天。主密钥离线备份两份（6.2 第 11 条）。
- **端口和 HTTPS**：
  - 普通用户默认不能占用 80 端口。要么请管理员在服务器上改一次系统设置，要么直接用 8080。
  - **v1 先用 HTTP，HTTPS 以后再说**（2026-10-17 你定的，6.2 第 18 条）。所以只在内网开放，不对外网。以后要上 HTTPS 时，用 Caddy 自带的内网证书或公司域名的正式证书，改 Caddy 配置就行，代码不用动。
- **验证情况**：
  - 已经在开发机上用 rootless Podman 构建并跑过：api 镜像（387MB）；浏览器基础镜像（1.25GB），Chrome 的 sandbox 在默认配置下就能开；PostgreSQL 18。
  - 还没验证：Quadlet（开发机的 Podman 版本太旧，要等服务器）、备份和恢复。M4 部署时做，并且演练一次从备份恢复。

## 3. 技术选型

npm 包的版本号都在 2026-10-17 用 `npm view` 核对过。开工时锁进 lockfile，以后升级单独做，先跑回归。

| 层 | 选择 | 没选的 | 理由 |
|---|---|---|---|
| 语言 | TypeScript 全栈，Node 24 LTS | Python | 前后端共享类型和校验规则；下面的库都是 TypeScript 一等支持；原型本来就是 TypeScript |
| 前端 | 定稿原型直接改造：Vite 8 + React 19 + Tailwind v4 + shadcn 预设 `buKEvLs` | 重写 | 页面和交互已经和你对齐过，只换数据来源 |
| 前端补充 | 表单库 React Hook Form；Markdown 显示用 shadcn 官方的 Typeset 样式加一个渲染库 | — | 组件库里没有，按 UI 规范属于例外，要你确认（6.2 第 15 条） |
| 前后端通信 | tRPC 11.19 | REST + OpenAPI | 前后端在同一个仓库，类型直接共享，不用另写接口文档 |
| 实时推送 | SSE（tRPC 订阅，断线自动续传） | WebSocket | 推送是单向的；跨进程广播用 PostgreSQL 的 LISTEN/NOTIFY。远程画面例外，走 WebSocket |
| 后端框架 | Hono 4.13 | Express、Fastify、NestJS | 轻；webhook、文件上传下载这类普通路由也用它 |
| agent 引擎 | 自己写：session 引擎 + 工具网关 + 规则闸门 | Claude Agent SDK、Mastra、LangGraph、Hermes | 见 2.3.1 |
| 模型层 | Vercel AI SDK 7（`ai` 7.0）+ OpenRouter provider 3.1 + `ai-sdk-ollama` 4.5 | 直接调 OpenAI 兼容接口 | 多家模型统一的工具调用、流式输出、用量统计；出问题时仍可以绕过它，直接走 OpenAI 兼容接口 |
| MCP 客户端 | `@ai-sdk/mcp` 2.0 | 官方 MCP SDK | 和模型层同一套，stdio 和 HTTP 都支持 |
| 数据库 | PostgreSQL 18 | MySQL、SQLite | 一个库同时放业务数据、队列、等待表；是当前最新的正式大版本 |
| ORM | Drizzle 0.45（不低于 0.45.2，这个版本修了一个 SQL 注入漏洞） | Prisma | 写法贴近 SQL；任务队列能和业务写入放进同一个事务。Prisma 正在换大版本，风险高 |

## 5. 风险和对策

| 风险 | 影响 | 对策 |

| 平台风控：验证码、封 IP、封账号 | 搜不到；账号被封连带影响业务 | agent 用专用账号，不用员工的个人账号；人在服务器的 Chrome 里登录，平台看到的始终是同一台设备、同一个 IP；低频访问，每个账号并发 1；验证码只检测、转人工，不破解。1688 同时申请官方接口，亚马逊准备 Rainforest 备用 |

| Playwright MCP 还是 0.0.x 版本 | 升级后行为变化（0.0.83 就改过页面快照的返回方式） | 锁定版本，升级前跑回归 |

| 业务逻辑混进代码 | 换个岗位就要改代码，平台变成搜品专用工具 | 开发约定写明不许；每个里程碑验收时检查产品代码里有没有业务词；M4 要求两个业务上线都不改代码 |
| 人手 | 只有 1 名工程师，请假或离职就停摆 | 代码和文档都在仓库里；选的都是主流库；每个里程碑都有演示和记录 |
