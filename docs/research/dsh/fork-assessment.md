# 全量 fork DeepSeek Harness 的迁移评估

> 2026-11-05 补：看完这份评估后，用户决定整体替换。目标架构见同目录的 `target-architecture.md`，本文留作当时的评估记录。

> 评估日期 2026-11-04。dsh 看的是 `deepseek-ai/deepseek-harness` 的 master，提交 `8bd07339`（2026-11-03），版本 `0.2.2-alpha.3`；HeyAgent 看的是 main `13c3e8f`。dsh 的内容来自仓库里的架构文档、各包 README 和 `package.json`，**没有把 dsh 跑起来，也没有写任何试验代码**。工作量是粗估，标「未核实」的地方没有在 dsh 代码里确认。

## 结论

**不建议全量 fork。** fork 之后，我们自己的代码几乎全部要按 dsh 的插件写法重写一遍。dsh 的核心还要改四处：存储换成 Postgres、多进程加排队、多用户、关掉外发数据。改完以后基本合不回上游，等于自己养一份约 52 万行的代码。换来的东西（agent 循环、工具流程、压缩、模型适配、子 agent）我们大部分已经有了。

粗估：全量 fork 到「现有功能都能用、真实任务跑通」要 **6～10 周**。这期间新功能基本停下，之后还要一直维护 dsh 那部分代码。对比：继续用现在的引擎，从 dsh 按需借个别做法，每次是几天的事。

如果一定要试，建议先做第 9 节的「第 0 步」（约 1 周）。这一步只验证最关键的几处，过不了就停，损失可控。

## 2. 先更正我前面说过的几点

前面聊天时有几句不准，这次核对后更正：

- **上下文压缩我们已经有了**（`apps/server/src/engine/compact.ts`，M3 做的：接近上限时把早的大块工具输出换成摘要和文件引用）。所以「dsh 能补上压缩」这条好处不成立，最多是两边的做法可以对照着看。
- **子 agent 我们也已经有了**（`engine/subagents/`，迁移 0037）。
- **dsh 能做到每次运行各用一个浏览器**：「一次只能启用一个浏览器后端」指的是只能选一种后端，后端自己会按会话管各自的浏览器。
- **dsh 不是完全没有多身份**：`api/remote-access` 可以给非 owner 的访问者按资源配角色，分享会话的 `liveshare` 就用它。但它没有账号体系（注册、登录、密码、用户表），默认只有一个 owner。

## 3. 逐模块：fork 之后各要怎么办

说明：「换成 dsh 的」= 删掉我们的，用 dsh 现成的，但要按我们的需要改；「写成插件」= 业务逻辑大体保留，改成 dsh 的插件和接口；「留在外面」= 不进 dsh，原样保留，只改接口。工作量分三档：小（几天以内）、中（1～2 周）、大（2 周以上，或者有不确定的地方）。行数含测试。

### 3.1 agent 引擎（`apps/server/src/engine`，约 1.5 万行）

| 我们的部分 | dsh 对应 | fork 后怎么办 | 工作量 |
|---|---|---|---|
| 循环 `loop.ts`、提示词 `prompt.ts`、记录 `records.ts` / `sessions.ts` | `core/agent-loop`、`core/system-prompt`、`core/session` | 换成 dsh 的。但我们的运行记录（每步落库、实时显示、`log-text`、`digest`）要从 dsh 的会话事件重新投影出来，界面读的数据结构全变 | 大 |
| 模型 `model.ts`、结构化输出 `structured.ts` | `ctx.llm` + `llm-pi-ai` | 换成 dsh 的，等于把模型层从 AI SDK 换成 pi-ai。我们踩过的坑都要在新模型层上重新验证：自定义服务的 json_schema、OpenRouter `:batch` / `:free`、DeepSeek 的速度测试 | 大 |
| 规则 `rules.ts` / `rule-compile.ts`、`hooks.ts`、工具网关 `gateway.ts` | `tools/pre-execute` / `post-execute` 拦截点，`agent/turn-stopping` | 写成插件，挂在 dsh 的拦截点上。能对得上，但「固定阶段执行的代码规则」要逐条核对 dsh 的事件时机 | 中 |
| 内置工具、HTTP 工具、MCP（`tools/`、`http.ts`） | `ctx.tools`、`mcp/mcp-manager` | HTTP 工具写成插件；MCP 换成 dsh 的，但我们的工具配置存在库里、按任务挑，要接到 dsh 的 agent preset 上 | 中 |
| 挂起几天后继续（`waits.ts`、`humans.ts`、`stop-watch.ts`） | `ctx.agents.resume()` + inbox；`interaction`（向用户提问） | 写成插件。dsh 能从持久会话恢复，但「挂起时不占资源，几天后由别的 worker 接着跑」要配合第 4 节的多进程改造才成立 | 大 |
| 检查点、验收、结果复核（`verify.ts`、`outcome.ts`、`review.ts`、`checkpoint-sync.ts`） | 没有对应。`auto-review` 是「执行工具前让模型判断放不放行」，不是运行结束后的结果复核 | 写成插件 | 中 |
| 子 agent（`subagents/`） | `subagent` 家族、`agent-team` | 换成 dsh 的，或者把我们的逻辑写成 subagent 提供方。dsh 的子 agent 都在同一个进程里，团队成员共用一个工作目录 | 中 |
| 派活（`dispatch/`）、名额、队列（`queue.ts`、`worker-runtime.ts`） | 没有对应 | 写成插件，并依赖第 4 节的多进程改造 | 大 |
| 定时（`schedule.ts`） | `schedule`：到点往会话里发一条消息 | 写成插件，或者保留我们的。dsh 的定时任务是「主机拥有的提醒」，不是「到点开一次任务运行」 | 小 |
| 压缩（`compact.ts`） | `compaction` | 换成 dsh 的，或者把我们的保留成插件 | 小 |
| 密钥、通知（`secrets.ts`、`notify.ts`） | `credentials`（本地 yaml） | 凭据要换成我们库里加密存的那一套 | 中 |

### 3.4 前端（`apps/web`，约 3.5 万行页面和组件）

两种做法：

- **A. 前端留在外面（推荐，如果真要 fork）**：页面不动，后端接口尽量保持 tRPC。运行详情、会话记录这些读运行数据的页面，要改成读 dsh 会话事件投影出来的数据。工作量中等，集中在任务、会话、派活三块。
- **B. 换成 dsh 的界面体系**：dsh 的界面是它自己的客户端插件，没有用 shadcn。要么违反「只用 `buKEvLs`」的硬规则，要么把它的界面全部重做成 shadcn。不建议。

## 4. dsh 核心必须改的地方

这些是 fork 后不改就不能用的，而且都是改核心，以后合并上游最难的就是这些：

1. **存储换成 Postgres**：会话日志要实现 `SessionPersistence`（create / open / stat / list / export，单写入方、flush 后才算存好）；其他数据要换掉 `storage-json` / `storage-sqlite`；设置和凭据要从 `~/.dsh` 的 yaml 换到库里。dsh 的设置、插件管理、profile 都默认「本机有个 home 目录」，牵扯面广。工作量：大。
2. **多进程和排队**：dsh 是一个进程管所有会话，后台任务只在进程内存里。我们要 api 和多个 worker 分开、从 pg-boss 领活，挂起的运行能被别的 worker 接着跑。dsh 说明里写了「每个后端实例内每个会话只允许一个写入方」，跨进程要靠我们自己的租约保证。工作量：大，**不确定性最高**。
3. **多用户**：认证要从「启动 token 换 cookie，只有一个 owner」改成我们的账号登录（现在用 better-auth），每个用户一个 principal，再用 `remote-access` 给各类资源配角色。文档还写明 `dsh web --host 0.0.0.0` 不支持，部署方式要改。工作量：中到大。
4. **关掉外发数据**：
   - `session-log-deepseek`：用 DeepSeek 官方接口时，**默认会把会话日志增量上传给 DeepSeek**（请求体里的 `dsh_session_log` 字段）。文档原话是「仅当官方 API 不得接收会话日志后缀时才禁用它」。
   - DeepSeek 请求头带匿名安装 id 和会话 id。
   - 遥测（`session-telemetry-otel`）默认 `FEEDBACK_ONLY`，可以用环境变量关掉。
   - 公司内部数据必须全部关掉，并且每次合并上游都要复查有没有新增外发。

   工作量：小，但要一直盯着。
5. **Node 版本**：dsh 要求 `>=24.9`。容器里已经是 24，开发机要升级。工作量：小。

## 5. fork 能得到什么

- 一套设计很细的 agent 循环和工具执行流程：每次请求都能从日志原样还原，取消和失败重试的处理很完整。
- 现成的子 agent 和团队任务板、模型写脚本分派子 agent（workflow / PTC）、定时、后台任务、MCP 管理、技能、权限和审批、上下文压缩、重复调用提醒、工具超时。
- 插件化：以后要换某一块（比如换一种浏览器后端）有固定的接法。

对照我们现有的东西，**真正新增的主要是 workflow / PTC 运行时、团队任务板、更完整的审批和权限体系**。其余的我们都已经有了，只是写法不同。

## 6. 成本和风险

1. **重写量**：第 3 节里标「大」的有 8 处，基本覆盖了我们最核心、最难调的部分（引擎、模型层、浏览器、挂起、派活、固化流程、存储、多进程）。这些代码是一次次真实运行调出来的，重写后要重新调。
2. **模型层换掉**：AI SDK 换成 pi-ai，之前跑的速度测试（DeepSeek 测试任务 A/B/C）和各家模型的坑都要重测。
3. **合不回上游**：dsh 几乎每天都在提交（最近一次 2026-11-03）。核心的存储、多进程、认证一改，再合并上游的代价越来越高，最后基本等于放弃上游。dsh 后面做的修复和新功能（比如 Windows 桌面）就拿不到了。
4. **接手 52 万行别人的代码**：比我们自己的代码多 4 倍。出了问题要自己读懂、自己修，文档虽然多，但概念也多（Cordis、profile、组合包、patch、Typert、realm……）。
5. **alpha 和安全**：它自己说没做过安全审计，不能用于生产。fork 之后，这个责任就是我们的了。
6. **停工期**：迁移期间新功能基本停下，现在在用的 8080 环境要么一直跑旧版本，要么两套并行。

## 8. 三条路对比

| | A. 全量 fork | B. 把 dsh 当引擎嵌进 worker | C. 不迁，按需借做法 |
|---|---|---|---|
| 做法 | 第 3～7 节 | 一次运行交给 dsh 的 `headless` 或 `sdk` 模式跑循环，浏览器、桌面、HTTP 工具用插件接回我们的服务；用户、排队、复核、界面都还是我们的 | 继续用现在的引擎，看中 dsh 哪一块就读它的实现，改写进我们的代码（MIT 允许，保留版权声明） |
| 工作量 | 6～10 周 | 试验 2～3 天；真要接上约 2～4 周 | 每块几天 |
| 能得到 | dsh 全部能力 | dsh 的循环、工具流程、workflow / PTC | 只拿需要的 |
| 主要风险 | 第 6 节全部 | 两套会话记录要对齐；挂起几天后继续，要靠我们存下 dsh 的会话再恢复 | 几乎没有 |
| 上游更新 | 基本拿不到 | 能跟（只用它公开的 SDK 接口） | 不涉及 |

建议顺序：**C 为主**。如果想要 dsh 的循环，就先做 B 的 2～3 天试验。A 只在 B 证明 dsh 的循环明显比我们的好、而且 B 的接法不够用时再考虑。

## 9. 如果仍要做 A：先做第 0 步，过不了就停

第 0 步（约 1 周）在 fork 里只做最关键、最不确定的四件事，每件都有明确的过关标准：

1. **会话存进 Postgres**：实现一个 `SessionPersistence` 后端，跑通 dsh 自带的存储测试。
2. **跨进程恢复**：进程 A 跑到一半挂起后退出，进程 B 从库里恢复同一个会话接着跑完，记录不丢、不重复。
3. **外发全部关掉**：抓包确认，一次运行中除了我们配置的模型服务地址，不会连任何外部地址。
4. **一个真实浏览器任务跑通**：用我们的浏览器池写一个最小的浏览器后端插件，跑 DeepSeek 测试任务 A。和现在的引擎比耗时（现在约 124 秒），不能明显变慢。

四件都过了，再决定要不要进第 1 阶段；有一件过不了就停，回到 B 或 C。

## 10. 没核实的

- dsh 在一个进程里同时跑几十个会话时的内存和性能，文档里没有数据。
- `SessionPersistence` 能不能干净地落到 Postgres 上（比如 flush、单写入方、generation 迁移这些语义），只读了说明，没读实现。
- dsh 的会话从持久存储恢复后，正在等的工具调用（比如等人回复）能不能接着等，只看到 `resume()` 的说明。
- `llm-pi-ai` 对 OpenRouter 的 usage（缓存 token）、结构化输出的支持程度。
- 改动 dsh 核心以后，它自带的测试（vitest 多套配置）有多少还能用来防回归。
