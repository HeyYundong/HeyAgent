# 运行结果：「状态」和「结果」分开（开发说明，2026-10-20）

> **状态：草稿，等用户确认。** 起因：用户 2026-10-20 发现「任务明明没有完成，会话里却标成【已完成】」，派活里也有很多单「办完」了，其实没办成。
> 用户 2026-10-20 已经定下的：
> 1. 会话和派活单都把**状态**（流程）和**结果**（事情办没办成）**拆成两列**；
> 2. 运行结束时做一次**轻量复核**，**默认开**，任务里可以关；
> 3. **结果导向**：任务要的东西没拿到，就算**没办成**。比如要找一个商品，没找到就是没办成，「确认没有」也一样；
> 4. **部分办成**的派活单**不自动重试**；
> 5. 已经结束的运行和派活单**补上结果**，「没核实」的**再跑一遍复核**；
> 6. 8080 的 pod 先不动，这次做完再一起重建。
>
> 文中写「现在」的，都是读 origin/main（bc131e0）的代码确认过的。

## 0. 一页纸

| # | 做什么 | 一句话 |
|---|---|---|
| 1 | **结果单独一列** | `sessions.outcome`、`work_items.outcome`：办成 / 部分办成 / 没办成 / 没核实；状态只管流程，「已完成」改叫「已结束」 |
| 2 | **收尾必须报结果** | 新内置工具 `run.finish`：agent 填结果、对照目标写依据。只回一段文字不调它的，提醒一次；还是不调，结果交给复核定 |
| 3 | **硬规则兜底** | 检查点：有没达成的或者全部跳过，记没办成；部分跳过，最多记部分办成。被派的任务声明了「要交回的结果」，缺了就记没办成 |
| 4 | **轻量复核** | 便宜模型看目标、检查点、agent 的报告和最后几步工具输出，判办成 / 部分 / 没办成 / 说不准。只能往低判，不能往高判；说不准的记没核实 |
| 5 | **派活跟着结果走** | 单的结果 = 运行的结果；部分办成和没办成都不重试；派活方叫醒时、`work.list` 里都能看到结果和原因 |
| 6 | **人能改结果** | 负责人可以在运行详情里把结果改掉（比如把没核实改成办成），要写一句理由，记进过程记录 |
| 7 | **补旧数据** | 迁移按规则补结果；另外一个命令对「没核实」的旧运行跑复核，先报预计花费，确认后再跑 |

## 1. 现在的样子（origin/main bc131e0）

- 运行状态 `run_status`：`running` `needs_human` `waiting` `verifying` `done`（已完成）`incomplete`（没完成，10-19 加的，0afb4f5）`failed`。
- 记「没完成」只有三种情况（`engine/loop.ts` 的 `finishRun` / `incompleteInTx`）：
  1. agent 调了 `run.not_done`；
  2. 被派的运行用 `work.report` 报了 `not_done`；
  3. 检查点兜底：有没勾的，或者全部跳过。
- **其余情况，agent 只要回一段文字、不再调工具，就记「已完成」。** 有四个漏洞：
  - ① agent 嘴上说「没找到」「只做了一部分」，但没调工具；
  - ② 任务没设检查点，没有任何兜底；
  - ③ 检查点部分跳过，算完成；
  - ④ 检查点是 agent 自己勾的，只有配了三方验收（`engine/verify.ts`）才有人核对。
- 派活单（`engine/dispatch/settle.ts`）：运行「已完成」，单就记「办完」，不管有没有用 `work.report` 交回任何结果。被派的任务一般没设检查点，所以①②全中。
- 8080 的 pod 比 0afb4f5 还旧：库里的 `run_status` 没有 `incomplete`。R-1-1 的 5 个检查点全部跳过，记的还是「已完成」。

## 2. 结果（outcome）

### 2.1 取值

| 值 | 显示 | 什么时候 |
|---|---|---|
| `achieved` | **办成** | 有依据：三方验收通过；或者 agent 报办成，且复核判办成；复核关着时，要检查点全部达成 |
| `partial` | **部分办成** | agent 报部分办成；或者检查点部分跳过；或者复核判部分办成 |
| `not_achieved` | **没办成** | agent 报没办成（`run.finish` / 旧的 `run.not_done` / `work.report not_done`）；检查点有没达成的或者全部跳过；缺必交的结果；复核判没办成；运行出错或取消 |
| `unverified` | **没核实** | agent 说办成了，但没有依据：没设检查点、复核关着或者复核说不准、没配复核模型 |
| 空 | — | 运行还没结束 |

**结果导向**（用户 2026-10-20 定的）：判结果只看任务目标要的东西拿没拿到，不看 agent 有多努力。要找商品，没找到就是没办成，确认「没有」也一样。这句话同时写进 `run.finish` 的说明、系统提示词和复核提示词。

### 2.2 状态（流程）

- `done` 的显示从「已完成」改成「**已结束**」。
- `incomplete` 不再写入，迁移把它改成 `done`，结果记 `not_achieved`；原因还在 `sessions.error`。Postgres 的枚举值删不掉，留着不用；`ENDED_RUN_STATUSES` 和 `isRunEnded` 照旧认它。
- `failed` 显示「出错」，结果记 `not_achieved`，原因就是错误信息。
- 取消的运行，状态照旧，结果记 `not_achieved`（原因「人取消了」）。

### 2.3 数据

迁移 `0024_run_outcome`：

- `sessions` 加 `outcome`（新枚举 `run_outcome`，可空）、`outcome_reason text`、`outcome_by`（`agent` / `rule` / `review` / `verify` / `human`，记是谁定的）、`review jsonb`（复核报告：结论、理由、模型、token）。
- `work_items` 加 `outcome`（同一个枚举）和 `outcome_reason`。
- `work_fail_kind` 加 `partial`、`missing_result`。
- 补旧数据：见第 7 节。

## 3. 收尾：`run.finish`

### 3.1 工具

内置工具 `run.finish`（风险 read，每个运行都自动带上；替代 `run.not_done`，旧运行快照里的 `run.not_done` 照旧能用，等价于 `run.finish outcome=not_achieved`）：

```
outcome: "achieved" | "partial" | "not_achieved"
summary: string            // 做了什么、结果在哪（就是现在最后那段总结）
evidence: string           // 对照目标逐条说依据：拿到了什么、在哪能看到；没拿到的写清楚
reason?: string            // partial / not_achieved 必填：缺了什么、为什么
```

调了它，运行就到此结束（和现在的 `run.not_done` 一样，在收尾的事务里写最终状态），不再调模型。

### 3.2 只回文字不调 `run.finish`

- 第一次：引擎追加一条 user 消息「要结束请调用 run_finish 报结果（办成 / 部分办成 / 没办成），并对照目标写依据」，再跑一轮。
- 还是只回文字：当作「agent 没报结果」，`summary` 就用那段文字，结果交给第 4、5 节的规则和复核去定；复核关着时记**没核实**。
- 三方验收（「agent 说做完了」的规则）照旧在 agent 说完之后跑。`run.finish outcome=achieved` 也算「说做完了」，会触发验收。

### 3.3 提示词

把现在 `prompt.ts` 里「做不成就调用 run_not_done…」那一行改成：

> 结束时一定调用 run_finish 报结果。只看任务目标要的东西拿没拿到：拿到了是办成，拿到一部分是部分办成，没拿到（包括确认「没有」）是没办成，并写清原因。不要把没做成说成做完了。

被派来的运行里，「办不成就用 work_report 报 not_done」改成「办不成就调用 run_finish 报没办成」；`work.report` 只用来交结构化结果（`not_done` 照旧认，兼容旧运行）。

## 4. 硬规则（在收尾的事务里，复核之前）

按顺序，取最低的那个（没办成 < 部分办成 < 没核实 < 办成）：

1. agent 的报告（`run.finish` / `run.not_done` / `work.report not_done`）。
2. 检查点：
   - 有没达成的，或者全部跳过 → 没办成（现在的规则，不变）；
   - 部分跳过（其余都达成）→ 最多部分办成（**改**：现在算完成）；
   - 全部达成 → 不压低。
3. 被派的运行：被派任务声明的「要交回的结果」里，必填的没用 `work.report` 交 → 没办成（`missing_result`，原因写「缺结果：价格、链接」）。
4. 三方验收通过 → 不再跑复核，结果就是第 1–3 条的结论（agent 报办成、规则没压低，就是办成）。

已经是没办成的不再复核：只能往低判，没办成没有更低的了。

## 5. 轻量复核

### 5.1 什么时候跑

运行正常结束，硬规则以后的结论是「办成」「部分办成」或「没核实」，任务开着复核（默认开），也没有配三方验收。

### 5.2 怎么跑

- 模型：新的默认模型角色 `review`（设置 → 模型，「复核模型」），建议选便宜的模型（Haiku 这一档）；任务里也可以单独选。没配复核模型就不跑，结论落到「没核实」。不要求和执行模型不是同一家（这不是三方验收）。
- 输入（复用 `verify.ts` 收集证据的那部分）：任务标题和目标；每条检查点（状态、记录、跳过理由）；agent 的 `run.finish`（或最后那段文字）；最后 N 步工具调用的输入和输出（摘录，总长有上限）；这次运行的产物清单；派活参数和交回的结果。不带截图（省钱；以后再说）。
- 输出（结构化，`callStructured`）：`verdict`（`achieved` / `partial` / `not_achieved` / `unsure`）加 `reason`（一两句话，指出依据或缺了什么）。
- 结论：`min(第 4 节的结论, 复核结论)`，`unsure` 记没核实。复核**只能往低判**：agent 自己报没办成的，复核不会改成办成。
- 结果在运行详情里显示成一条「复核」过程记录，报告存进 `sessions.review`。
- 复核本身出错（模型报错、超时）：不重试，结论落到「没核实」，过程记录写原因。运行状态不受影响。

### 5.3 时机和花费

- 在收尾的事务**之后**跑（不占着事务等模型）：先把状态写成「已结束」、结果先写硬规则的结论，复核回来再更新结果。被派的运行要等复核完再结算派活单、叫醒派活方（见 6.2）。
- 花费：输入大约 5–15k token。按 Haiku 这一档的价格，每次大约 0.01–0.02 美元，用量记到这次运行的 token 和花费里。

### 5.4 任务设置

任务的「完成」区块里加一个开关「结束后让 AI 复核」（默认开）和「复核模型」（默认用设置里的）。配了三方验收的任务，开关不起作用，旁边写「已有三方验收」。

## 6. 派活

### 6.1 被派任务：要交回的结果

`tasks.dispatch` 加 `results: [{ name, description, required }]`（最多 20 个，和参数同一写法）。派活页、任务的派活设置里可以编辑。

- 系统提示词「派来的活」一节列出要交回的结果。
- `work.report` 交的字段名不在声明里的，照收（兼容现在的写法）。
- 必填的没交：按第 4 节第 3 条记没办成。

### 6.2 单的结果

| 运行的结果 | 单的状态 | 单的结果 | 重试 |
|---|---|---|---|
| 办成 | 办完 | 办成 | — |
| 没核实 | 办完 | 没核实（派活页显眼地标出来） | — |
| 部分办成 | 没办成（`partial`） | 部分办成 | 不重试 |
| 没办成（agent 报的、规则判的、复核判的） | 没办成（`not_done` / `missing_result`） | 没办成 | 不重试 |
| 运行出错 | 照现在：还有重试次数就排队重试，没有就没办成（`error`） | 没办成 | 照现在 |

- 派活页：列表加「结果」列；状态筛选「在办 / 办完 / 没办成」不变，另外加结果筛选，可以只看「没核实」。
- `work.done` 叫醒派活方时、`work.list` 的每一行，都带上 `outcome` 和 `outcomeReason`。派活方的提示词里加一句：「拿到没办成或没核实的单，要自己判断要不要重派或者报给人」。

## 7. 补旧数据

迁移 `0024` 里（不花钱）：

| 旧记录 | 补成 |
|---|---|
| 运行 `incomplete` | 状态改成 `done`，结果没办成，原因 = `error` |
| 运行 `failed` | 结果没办成，原因 = `error` |
| 运行 `done`，检查点有没达成的或者全部跳过 | 没办成（R-1-1 就是这种） |
| 运行 `done`，检查点部分跳过 | 部分办成 |
| 运行 `done`，三方验收通过 | 办成 |
| 运行 `done`，其余 | 没核实，等下面的复核 |
| 派活单 | 按它最后那次运行的结果补；单的状态不改（已经办完的单不会因为补数据变成没办成，只有结果列显示没办成 / 没核实） |

另外加一个命令 `pnpm --filter server outcome:review`，对「没核实」的旧运行跑一遍复核：

- 先列出有多少条、预计花费，加 `--yes` 才真跑；默认最多 200 条（`--limit` 可改）。
- 复核结论只写结果列，不改单的状态，不发通知，不叫醒派活方。
- 8080 重建以后由你决定什么时候跑（这次说明里不自动跑）。

全部用现有的 registry 组件，不需要走例外流程。

  - 办成：`outline` + `CircleCheckIcon`；
  - 部分办成：`secondary` + `CircleDotIcon`；
  - 没办成：`destructive` + `CircleXIcon`；
  - 没核实：`outline` + `CircleHelpIcon`；
  - 还没结束：「—」。
  
  悬停的 `Tooltip` 显示原因。筛选栏加结果筛选。

- **派活页**（`pages/work/`）：列表和详情同样加结果徽章和原因；`RUN_TEXT` 里 `done` 从「办完」改成「已结束」。

- **设置 → 模型**：默认模型里加「复核模型」。
- 首页 / 看板上凡是写「已完成」的地方，统一改成看结果。
- 使用手册（`pages/learn`）和接口文档同步更新。

## 10. 测试

- 单测：`finishRun` 的取最低逻辑（agent × 检查点 × 必交结果 × 验收 × 复核，所有组合都过一遍）；`run.finish` 校验（partial / not_achieved 没写 reason 要报错）；只回文字时提醒一次，再回文字就记没核实；迁移补数据的每一行。
- 派活：部分办成和没办成都不重试；缺必交结果记 `missing_result`；叫醒派活方时带上结果。
- 真模型试一遍（Haiku）。拿用户说的那种情况造例子，因为真实的派活单已经找不到了：
  1. 要找一个不存在的商品，agent 回「没找到」但不报，复核要判**没办成**；
  2. 被派的任务没设检查点，也没交必填结果，要记**没办成**（`missing_result`）；
  3. A–Z 图片放进金山文档，做完一半就说完了，要记**部分办成**或者**没办成**；
  4. 真的办成了的，要记**办成**，不能被复核误判压低。
- 界面：会话列表、运行详情（改结果）、派活页，浅色和暗色、窄屏都看一遍。

## 11. 要你确认的（括号里是我的建议）

1. `done` 的显示从「已完成」改成「**已结束**」，`incomplete` 合并进 `done` 加结果没办成？（建议这样做：状态列以后不会再出现「完成 / 没完成」这种结果字眼）
2. 「没核实」的派活单，单的状态记**办完**还是**没办成**？（建议办完，但在结果列显眼地标出来：大多数时候其实是办成了，只是没依据；记没办成会让派活方重复派）
3. agent 只回文字不调 `run.finish` 的，**提醒一次**再定，还是不提醒、直接交给复核？（建议提醒一次：多花一轮，但大多数模型会补上报告，复核也更准）
4. 负责人能**手动改结果**（第 8 节），要不要？（建议要：复核也会判错，人要有最后的决定权）
5. 复核**不带截图**，只看文字证据？（建议先不带：带图贵好几倍；浏览器任务的证据大多在工具输出里。以后再加「复核看最后一张截图」的选项）
