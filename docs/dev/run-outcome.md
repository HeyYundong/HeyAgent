# 运行结果：「状态」和「结果」分开（开发说明，2026-10-20）

> **状态：用户 2026-10-20 确认并开工，已实现（分支 `worktree-run-outcome`），等用户确认后合到 main。** 起因：用户 2026-10-20 发现「任务明明没有完成，会话里却标成【已完成】」，派活里也有很多单「办完」了，其实没办成。
> 用户 2026-10-20 已经定下的：
> 1. 会话和派活单都把**状态**（流程）和**结果**（事情办没办成）**拆成两列**；
> 2. 运行结束时做一次**轻量复核**，**默认开**，任务里可以关；
> 3. **结果导向**：任务要的东西没拿到，就算**没办成**。比如要找一个商品，没找到就是没办成，「确认没有」也一样；
> 4. **部分办成**的派活单**不自动重试**；
> 5. 已经结束的运行和派活单**补上结果**，「没核实」的**再跑一遍复核**；
> 6. 8080 的 pod 先不动，这次做完再一起重建。
>
> 文中写「现在」的，都是读 origin/main（bc131e0）的代码确认过的。

> **同一天又简化了一次（见下一节），下面第 0、2–10 节已经按简化以后的样子改过；第 1 节是改之前的样子，留着备查。**

## 2026-10-20 简化：只有办成 / 没办成

用户 2026-10-20 觉得四种结果太复杂，定下（分支 `worktree-outcome-two-values`，迁移 `0026_outcome_two_values`）：

1. **结果只有两种：办成（`achieved`）、没办成（`not_achieved`）。** 照旧结果导向：目标要的东西拿到了是办成；其余都是没办成，包括只拿到一部分、确认「没有」。细节写在原因里（例如「只拿到价格，缺链接」）。
2. **没核实算没办成。** 没有能证明办成的依据，就记没办成，原因写清楚（例如「证据不足：…」「没配复核模型，没能确认办成」）。
3. **每个任务都必须有复核模型，复核一定做。** 任务里「结束后让 AI 复核」的开关去掉（`tasks.review_enabled` 删了）。只有三方验收通过的不复核（直接办成）。
4. **已经结束的运行都能改结果**（已结束、出错、取消的都行，不只是旧数据）：负责人和主管在运行详情的「结果」区块，或者会话列表那一行的「更多」菜单里，改成办成或没办成，要写理由。

## 1. 现在的样子（origin/main bc131e0）

- 运行状态 `run_status`：`running` `needs_human` `waiting` `verifying` `done`（已完成）`incomplete`（没完成，10-19 加的，0afb4f5）`failed`。
- 记「没完成」只有三种情况（`engine/loop.ts` 的 `finishRun` / `incompleteInTx`）：
  1. agent 调了 `run.not_done`；
  2. 被派的运行用 `work.report` 报了 `not_done`；
  3. 检查点兜底：有没勾的，或者全部跳过。
- **其余情况，agent 只要回一段文字、不再调工具，就记「已完成」。** 有四个漏洞：
  - ① agent 嘴上说「没找到」「只做了一部分」，但没调工具；
  - ② 任务没设检查点，没有任何兜底；
  - ③ 检查点部分跳过，算完成；
  - ④ 检查点是 agent 自己勾的，只有配了三方验收（`engine/verify.ts`）才有人核对。
- 派活单（`engine/dispatch/settle.ts`）：运行「已完成」，单就记「办完」，不管有没有用 `work.report` 交回任何结果。被派的任务一般没设检查点，所以①②全中。
- 8080 的 pod 比 0afb4f5 还旧：库里的 `run_status` 没有 `incomplete`。R-1-1 的 5 个检查点全部跳过，记的还是「已完成」。

## 2. 结果（outcome）

### 2.1 取值

| 值 | 显示 | 什么时候 |
|---|---|---|
| `achieved` | **办成** | 三方验收通过；或者 agent 报办成、硬规则（第 4 节）都过了、复核也判办成 |
| `not_achieved` | **没办成** | 其余都是：agent 报没办成（`run.finish`，含旧说明的 `partial` / 旧的 `run.not_done` / `work.report not_done`）；检查点有没达成的或者有跳过的；缺必交的结果；复核判没办成、证据不足、复核出错（重试一次还出错）、没有复核模型、复核超时没结果；运行出错或取消 |
| 空 | —（运行还没结束）/ **复核中**（运行已结束、`review.pending`） | |

**结果导向**（用户 2026-10-20 定的）：判结果只看任务目标要的东西拿没拿到，不看 agent 有多努力。要找商品，没找到就是没办成，确认「没有」也一样；只拿到一部分也是没办成，原因写清拿到了什么、缺什么。这句话同时写进 `run.finish` 的说明、系统提示词和复核提示词。

### 2.2 状态（流程）

- `done` 的显示从「已完成」改成「**已结束**」。
- `incomplete` 不再写入，迁移把它改成 `done`，结果记 `not_achieved`；原因还在 `sessions.error`。Postgres 的枚举值删不掉，留着不用；`ENDED_RUN_STATUSES` 和 `isRunEnded` 照旧认它。
- `failed` 显示「出错」，结果记 `not_achieved`，原因就是错误信息。
- 取消的运行，状态照旧，结果记 `not_achieved`（原因「某某取消了这次运行」，`outcome_by = human`）。

### 2.3 数据

迁移 `0024_run_outcome`：

- `sessions` 加 `outcome`（新枚举 `run_outcome`，可空）、`outcome_reason text`、`outcome_by`（`agent` / `rule` / `review` / `verify` / `human`，记是谁定的）、`review jsonb`（复核报告：结论、理由、模型、token）。
- `work_items` 加 `outcome`（同一个枚举）和 `outcome_reason`。
- `work_fail_kind` 加 `partial`、`missing_result`。
- 补旧数据：见第 7 节。

迁移 `0026_outcome_two_values`（简化）：`tasks.review_enabled` 删掉；`run_outcome` 的 `partial` `unverified` 留着不用；旧数据见第 7 节。

## 3. 收尾：`run.finish`

### 3.1 工具

内置工具 `run.finish`（风险 read，每个运行都自动带上；替代 `run.not_done`，旧运行快照里的 `run.not_done` 照旧能用，等价于 `run.finish outcome=not_achieved`）：

```
outcome: "achieved" | "not_achieved"   // 旧说明里的 "partial" 照收，当 not_achieved
summary: string            // 做了什么、结果在哪（就是现在最后那段总结）
evidence: string           // 对照目标逐条说依据：拿到了什么、在哪能看到；没拿到的写清楚
reason?: string            // not_achieved 必填：拿到了什么、缺了什么、为什么
```

调了它，运行就到此结束（和现在的 `run.not_done` 一样，在收尾的事务里写最终状态），不再调模型。

### 3.2 只回文字不调 `run.finish`

- 第一次：引擎追加一条 user 消息「要结束请调用 run_finish 报结果（办成 / 没办成），并对照目标写依据」，再跑一轮。
- 还是只回文字：当作「agent 没报结果」，`summary` 就用那段文字，结果交给第 4、5 节的规则和复核去定。
- 三方验收（「agent 说做完了」的规则）照旧在 agent 说完之后跑。`run.finish outcome=achieved` 也算「说做完了」，会触发验收。

### 3.3 提示词

把现在 `prompt.ts` 里「做不成就调用 run_not_done…」那一行改成：

> 结束时一定调用 run_finish 报结果，结果只有办成、没办成两种。只看任务目标要的东西拿没拿到：都拿到了是办成；没拿到（包括确认「没有」）是没办成；拿到一部分也算没办成，在 reason 写清拿到了什么、缺什么。不要把没做成说成做完了。

被派来的运行里，「办不成就用 work_report 报 not_done」改成「办不成就调用 run_finish 报没办成」；`work.report` 只用来交结构化结果（`not_done` 照旧认，兼容旧运行）。

## 4. 硬规则（在收尾的事务里，复核之前）

下面有一条不过就是**没办成**（定论，不再复核；几条原因用「；」连起来，谁定的按 agent 报的 > 缺结果 > 检查点）：

1. agent 的报告（`run.finish` 报没办成或者旧说明的部分办成 / `run.not_done` / `work.report not_done`）。
2. 检查点：有没达成的、全部跳过的、部分跳过的（原因「N 个检查点跳过，只办成了一部分：…」）→ 没办成；全部达成不压低。三方验收通过的不按检查点判（验收员已经逐条核对过跳过理由）。
3. 被派的运行：被派任务声明的「要交回的结果」里，必填的没用 `work.report` 交 → 没办成（`missing_result`，原因写「缺结果：价格、链接」）。

都过了：

4. 三方验收通过 → 办成（定论），不再复核。
5. 其余（agent 报办成，或者只回文字说做完了；检查点全部达成也一样，检查点是 agent 自己勾的）→ 一定复核（第 5 节），复核判办成才算办成。

## 5. 轻量复核

### 5.1 什么时候跑

运行正常结束，硬规则都过了（第 4 节第 5 条）：agent 说办成了、没有三方验收通过。每个任务都要跑，没有开关。

### 5.2 怎么跑

- 模型：任务的复核模型（必填）；快照里没有的（2026-10-20 以前的任务、没选过）用默认模型角色 `review`（设置 → 模型，「复核模型」，新任务预填它），默认 `openrouter/deepseek/deepseek-v4.1-flash`（能看图、很便宜，用户 2026-10-20 指定；不用 `:batch` 版本）。复核模型不能看图时，就不带截图，过程记录里写一句。都没有：开始运行时就拒绝；万一结束时没有（开始以后默认复核模型被清掉了），结论是没办成（「没配复核模型，没能确认办成」）。不要求和执行模型不是同一家（这不是三方验收）。
- 输入（复用 `verify.ts` 收集证据的那部分）：任务标题和目标；每条检查点（状态、记录、跳过理由）；agent 的 `run.finish`（或最后那段文字）；最后 N 步工具调用的输入和输出（摘录，总长有上限）；这次运行的产物清单；派活参数和交回的结果；**最后一张截图**（用了浏览器 / 电脑的运行，用户 2026-10-20 定的）。
- 输出（结构化，`callStructured`）：`verdict`（`achieved` / `not_achieved`）加 `reason`（一两句话：办成的指出依据；没办成的写清拿到了什么、缺了什么，证据不足的写缺哪样证据）。提示词：证据不足、拿不准都判 `not_achieved`，不要猜。
- 结论：复核判办成 → 办成，否则没办成，都记 `outcome_by = review`。复核只在硬规则说办成时跑，所以 agent 自己报没办成的不会被改成办成。
- 结果在运行详情里显示成一条「复核」过程记录，报告存进 `sessions.review`（旧报告的 `partial` / `unsure` 照原样显示）。
- 复核本身出错（模型报错、超时）：重试一次（两次的用量都算）；还出错，结论是没办成（「复核出错，没能确认办成：…」），过程记录写原因。运行状态不受影响。

### 5.3 时机和花费

- 在收尾的事务**之后**跑（不占着事务等模型）：先把状态写成「已结束」、结果先空着、写复核标记（`review.pending`，页面显示「复核中」），复核回来再写结果。被派的运行要等复核完再结算派活单、叫醒派活方（见 6.2）。
- worker 中途没了、复核一直没回来：清扫（`work.sweep`，每分钟）发现复核标记超过 10 分钟，清掉标记、结果记没办成（「复核没有结果（worker 可能中途重启了），没能确认办成」，复核期间人已经改过结果的不动），通知负责人，再结算被派的单。
- 花费：文字加一张截图，输入大约 5–15k token。按 deepseek-v4.1-flash 的价格（每百万 token 输入 0.0376 美元、输出 0.08 美元），每次不到 0.001 美元。用量记到这次运行的 token 和花费里。

### 5.4 任务设置

任务的「完成」区块里有「复核模型」（必填，新任务和没选过的旧任务先填上设置里的默认复核模型）。2026-10-20 简化以前还有开关「结束后让 AI 复核」，已经去掉。配了三方验收的任务照样要选复核模型：验收通过的不复核，其余（比如规则没触发验收）照样复核。

## 6. 派活

### 6.1 被派任务：要交回的结果

`tasks.dispatch` 加 `results: [{ name, description, required }]`（最多 20 个，和参数同一写法）。派活页、任务的派活设置里可以编辑。

- 系统提示词「派来的活」一节列出要交回的结果。
- `work.report` 交的字段名不在声明里的，照收（兼容现在的写法）。
- 必填的没交：按第 4 节第 3 条记没办成。

### 6.2 单的结果

| 运行的结果 | 单的状态 | 单的结果 | 重试 |
|---|---|---|---|
| 办成 | 办完 | 办成 | — |
| 没办成（agent 报的含只拿到一部分、规则判的、复核判的、复核没能确认的） | 没办成（`not_done` / `missing_result`） | 没办成 | 不重试 |
| 运行出错 | 照现在：还有重试次数就排队重试，没有就没办成（`error`） | 没办成 | 照现在 |
| 人取消、人选不继续、人判验收失败 | 没办成（`cancelled_run`） | 没办成 | 不重试（清扫补写时按 `outcome_by = human` 认） |
| 开不了运行（例如任务没设复核模型） | 没办成（`error`） | 没办成，原因「没能开始运行：…」 | 不重试 |

## 8. 界面

全部用现有的 registry 组件，不需要走例外流程。

- **会话列表**（`pages/sessions/list.tsx`）：在「状态」后面加一列「结果」。徽章按 `docs/ui-rules.md` 第 4 节的建议映射：
  - 办成：`outline` + `CircleCheckIcon`；
  - 没办成：`destructive` + `CircleXIcon`；
  - 复核中（运行已结束、复核还在跑）：`secondary` + `Spinner`；
  - 还没结束：「—」。
  
  悬停的 `Tooltip` 显示原因。筛选栏加结果筛选（办成 / 没办成）。每行最后有「更多」菜单（`DropdownMenu`），已经结束的运行，负责人和主管能「改结果」（同运行详情的弹窗）；窄屏一条就是一个链接，在抽屉里改。
- **运行详情**（`pages/tasks/run-detail.tsx`）：标题旁边显示结果徽章；在「结果」区块里写原因、是谁定的（agent / 检查点 / 复核 / 验收 / 人），复核报告放在可以展开的 `Collapsible` 里。已经结束的运行（已结束、出错、取消的都行），负责人能点「改结果」：一个 `Dialog`，里面是 `RadioGroup` 选办成 / 没办成、`Textarea` 写理由（必填），改完记一条过程记录（`human`）。改结果只影响结果列，不重开运行；被派的单跟着改结果，不改单的状态。
- **派活页**（`pages/work/`）：列表和详情同样加结果徽章和原因；`RUN_TEXT` 里 `done` 从「办完」改成「已结束」。
- **任务编辑**：「完成」区块加复核模型（`ModelCombobox`，必填，`FieldError` 提示「选一个复核模型」）；派活设置加「要交回的结果」（写法和参数一样）。
- **设置 → 模型**：默认模型里加「复核模型」（新任务默认用的复核模型）。
- 首页 / 看板上凡是写「已完成」的地方，统一改成看结果。
- 使用手册（`pages/learn`）和接口文档同步更新。

## 10. 测试

- 单测：硬规则（agent × 检查点 × 必交结果 × 验收，所有组合都过一遍）和复核结论（办成 / 没办成 / 旧的部分办成、说不准 / 出错）；`run.finish` 校验（not_achieved 没写 reason 要报错，旧的 partial 当没办成）；只回文字时提醒一次，再回文字交给复核；复核出错重试一次；没有复核模型不开始运行；迁移 0024 + 0026 补数据的每一行。
- 派活：没办成（含只拿到一部分）不重试；缺必交结果记 `missing_result`；复核超时记没办成；人取消的清扫补写不重试；叫醒派活方时带上结果。
- 真模型试一遍（Haiku）。拿用户说的那种情况造例子，因为真实的派活单已经找不到了：
  1. 要找一个不存在的商品，agent 回「没找到」但不报，复核要判**没办成**；
  2. 被派的任务没设检查点，也没交必填结果，要记**没办成**（`missing_result`）；
  3. A–Z 图片放进金山文档，做完一半就说完了，要记**没办成**（原因写做到哪了）；
  4. 真的办成了的，要记**办成**，不能被复核误判压低。
- 界面：会话列表、运行详情（改结果）、派活页，浅色和暗色、窄屏都看一遍。
