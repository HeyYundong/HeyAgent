## 2026-10-20 简化：只有办成 / 没办成

用户 2026-10-20 觉得四种结果太复杂，定下（分支 `worktree-outcome-two-values`，迁移 `0026_outcome_two_values`）：

1. **结果只有两种：办成（`achieved`）、没办成（`not_achieved`）。** 照旧结果导向：目标要的东西拿到了是办成；其余都是没办成，包括只拿到一部分、确认「没有」。细节写在原因里（例如「只拿到价格，缺链接」）。

## 3. 收尾：`run.finish`

### 3.1 工具

内置工具 `run.finish`（风险 read，每个运行都自动带上；替代 `run.not_done`，旧运行快照里的 `run.not_done` 照旧能用，等价于 `run.finish outcome=not_achieved`）：

```
outcome: "achieved" | "not_achieved"   // 旧说明里的 "partial" 照收，当 not_achieved
summary: string            // 做了什么、结果在哪（就是现在最后那段总结）
evidence: string           // 对照目标逐条说依据：拿到了什么、在哪能看到；没拿到的写清楚
reason?: string            // not_achieved 必填：拿到了什么、缺了什么、为什么
```

调了它，运行就到此结束（和现在的 `run.not_done` 一样，在收尾的事务里写最终状态），不再调模型。

### 3.2 只回文字不调 `run.finish`

- 第一次：引擎追加一条 user 消息「要结束请调用 run_finish 报结果（办成 / 没办成），并对照目标写依据」，再跑一轮。
- 还是只回文字：当作「agent 没报结果」，`summary` 就用那段文字，结果交给第 4、5 节的规则和复核去定。
- 三方验收（「agent 说做完了」的规则）照旧在 agent 说完之后跑。`run.finish outcome=achieved` 也算「说做完了」，会触发验收。

### 3.3 提示词

把现在 `prompt.ts` 里「做不成就调用 run_not_done…」那一行改成：

> 结束时一定调用 run_finish 报结果，结果只有办成、没办成两种。只看任务目标要的东西拿没拿到：都拿到了是办成；没拿到（包括确认「没有」）是没办成；拿到一部分也算没办成，在 reason 写清拿到了什么、缺什么。不要把没做成说成做完了。

被派来的运行里，「办不成就用 work_report 报 not_done」改成「办不成就调用 run_finish 报没办成」；`work.report` 只用来交结构化结果（`not_done` 照旧认，兼容旧运行）。

## 5. 轻量复核

### 5.1 什么时候跑

运行正常结束，硬规则都过了（第 4 节第 5 条）：agent 说办成了、没有三方验收通过。每个任务都要跑，没有开关。

### 5.2 怎么跑

- 模型：任务的复核模型（必填）；快照里没有的（2026-10-20 以前的任务、没选过）用默认模型角色 `review`（设置 → 模型，「复核模型」，新任务预填它），默认 `openrouter/deepseek/deepseek-v4.1-flash`（能看图、很便宜，用户 2026-10-20 指定；不用 `:batch` 版本）。复核模型不能看图时，就不带截图，过程记录里写一句。都没有：开始运行时就拒绝；万一结束时没有（开始以后默认复核模型被清掉了），结论是没办成（「没配复核模型，没能确认办成」）。不要求和执行模型不是同一家（这不是三方验收）。
- 输入（复用 `verify.ts` 收集证据的那部分）：任务标题和目标；任务写了交付物的，目标后面逐项列出「要交付的东西」，缺一项判没办成（2026-10-30，`docs/dev/task-structure.md` 第 1 节；三方验收的输入同样列出）；每条检查点（状态、记录、跳过理由）；agent 的 `run.finish`（或最后那段文字）；整次运行的过程记录（`engine/log-text.ts` 的 `reviewLog`，2026-10-28 改：最近 30 条详细，更早的每条压成一行、合计最多 1.2 万字，超了中间省略；`browser.batch` 逐步写出填的值，批里各步和批的汇总标清楚，免得当成做了两遍；固化流程跑的运行另有「固化流程的记录」：第几版、提交和核对、`ha.log`、停在哪。以前只给最近 30 条，长运行的前半段看不到，复核会判证据不足，见 `docs/dev/solidify.md` 第 20 节。**读数据的几步多给字数**（`readsData`）：`browser.fetch`、`browser.extract`、`browser.snapshot`、`browser.find`、`browser.clipboard_read` 和带了页面快照的 `browser.batch`，在详细的几条里合计 8000 字平分（每条 300～2000 字；2026-10-29 改成 12000 字按需分、每条 300～4000 字，见下面「读数据的工具」），更早压成一行的给两倍；排好版的 JSON 先压成一行（edeb8ce，`solidify.md` 21.3 第 1 条）；页面快照（`browser.snapshot` 的结果、批末尾的「页面快照：」）先用 `compactSnapshot` 压成文字行：去掉 `### Page`、代码块和 `[ref=…]` 等标记、只是容器的行，表格的一行各格用 `|` 连，输入框写「名字=值」，批写成「逐步 ✓ 最后的页面快照：…」（2026-10-29，`sub-agents.md` 21.6.5 第 4 条：agent 从批的快照里读到电话、评分，以前批只留逐步 ✓ / ✗，复核看不到这些值，把对的运行判成没办成）。复核的系统提示写明「最后的页面快照」是页面上真有的内容）；这次运行的产物清单；派活参数和交回的结果；**最后一张截图**（用了浏览器 / 电脑的运行，用户 2026-10-20 定的）。
- 输出（结构化，`callStructured`）：`verdict`（`achieved` / `not_achieved`）加 `reason`（一两句话：办成的指出依据；没办成的写清拿到了什么、缺了什么，证据不足的写缺哪样证据）。提示词：证据不足、拿不准都判 `not_achieved`，不要猜。复核输入总长上限 6 万字（2026-10-28 从 4 万放宽，过程记录覆盖整次运行以后要多一些；2026-10-29 放到 8 万，三方验收也用这个上限，见下面），超了从中间截。
- **读数据的工具**（2026-10-29，`log-text.ts` 的 `DATA_TOOLS`、`isDataTool`、`readsData`）：真模型验收里 agent 从工具结果里读到数据、全做对了，复核看不到这些值就判没办成（`sub-agents.md` 21.6.5 第 4 条）。除了上面几个浏览器工具，下面这些的结果也算读数据，多给字数：
  - 任务里配置的 **HTTP 工具、MCP 工具**（id 是主管起的，按运行快照里 `source = http / mcp` 认，`dataToolIdsOf`）；
  - `code.run`：给退出码那几行（写回了哪些文件、访问了哪些主机）和 **stdout**（脚本打印的结果，排好版的 JSON 先压成一行），stdout 太长的留开头 1/3、结尾 2/3（结果多半在末尾），stderr 和「脚本调的工具」各最多 300 字（`describeCodeRunOutput`）；
  - `file.read`：读到的文本内容（排好版的 JSON 先压成一行）；
  - 库流程 `routine.<短名>`：交回的值；
  - `work.list`（派出去的单的结果）、`browser.network_request`（一个请求的返回体）、`desktop.snapshot`、`desktop.clipboard`、`gallery.search` / `get` / `compare`、`compare.images` / `get` / `list`。
  - 不算的：`subagent.wait`（子 agent 交回的字段另有「子 agent」一节，`sub-agents.md` 9.2）、`skill.load`（是做法说明，不是数据）。记忆不是工具读的（系统提示里给），不在过程记录里。
  - **份额**：详细的几条里读数据的结果合计 12000 字（`DATA_OUTPUT_BUDGET`，原来 8000），每条 300～4000 字（原来 2000）。按需分（`shareBudget`）：从要得少的分起，每条最多拿「剩下的 ÷ 还没分的条数」，用不完的留给后面要得多的，所以短的结果多了也不浪费。放宽的理由：大家分同一个份额了；一个 HTTP / 接口的返回（几十条记录的 JSON）压成一行常有三四千字；最近 30 条全是读数据的时每条正好 400 字（不比原来的 300 字少），合计仍不超过 12000。过程记录最多大约 1.2 万（较早的）+ 最近 30 条的参数和别的结果 + 1.2 万（读数据的），输入总长上限从 6 万放到 8 万字（`EVIDENCE_PROMPT_MAX`，约 5～8 万 token）：复核用的便宜模型（deepseek-v4.1-flash 等）和验收模型上下文都在 12.8 万以上，一次花费一分钱上下；一般的运行远少于这些。
- **三方验收也这样**（2026-10-29，`verify.ts` 的 `loadEvidence`、`buildVerifyPrompt`）：以前三方验收取最近 60 条，每条参数、结果都按 300 字截原样 JSON，agent 靠的数据基本看不到。现在和复核用同一份过程记录（`reviewLog`、同样的 `REVIEW_LOG` 和读数据份额）：整次运行，最近 30 条详细、更早的压成一行，读数据的工具多给字数；标题写「整次运行共 n 条……」；系统提示加了和复核一样的几条「过程记录怎么读」（`LOG_FORMAT_NOTES`：#k 序号、批的汇总不是又做一遍、读数据的结果是工具真拿到的）；输入总长同样不超过 8 万字（以前没有上限，但只有 60 条 × 600 字）。预算和复核一样，不另设小的：验收要逐条检查点找证据（「有记录、文件或截图佐证的才算通过」），要的证据不比复核少。验收什么时候跑、给谁用、逐条判定的规则、几轮反问和交给负责人都没变，只是看到的证据更全。
- 结论：复核判办成 → 办成，否则没办成，都记 `outcome_by = review`。复核只在硬规则说办成时跑，所以 agent 自己报没办成的不会被改成办成。
- 结果在运行详情里显示成一条「复核」过程记录，报告存进 `sessions.review`（旧报告的 `partial` / `unsure` 照原样显示）。
- 复核本身出错（模型报错、超时）：重试一次（两次的用量都算）；还出错，结论是没办成，原因写「复核没做成（<错误>），结果没有核实，可以人工改结果。」（2026-10-30 起；以前是「复核出错，没能确认办成：…」，看起来像 agent 没做好），过程记录写原因。运行状态不受影响。
- **复核模型返回的格式不对**（2026-10-30，`sub-agents.md` 21.7.4 第 1 条；`engine/structured.ts`）：
  - 认得宽一点：给模型的 JSON Schema 照旧是严格的 `achieved` / `not_achieved`，解析时（`lenientEnum`）先去掉前后空白、引号、括号和句末标点、转小写、空格和连字符当下划线，再查同义写法表（`REVIEW_VERDICT_SYNONYMS`）：中文「办成 / 办成了 / 已办成 / 成功 / 完成 / 达成」→ `achieved`，「没办成 / 未办成 / 失败 / 未完成 / 部分办成 / 说不准 / 证据不足」→ `not_achieved`；英文 `success` / `succeeded` / `done` / `pass` → `achieved`，`not achieved` / `failed` / `failure` / `partial` / `unsure` → `not_achieved`（部分办成、说不准按复核的规矩本来就是没办成）。只认整个值对得上的，不从一句话里猜。系统提示末尾也再写一遍 verdict 只能原样写哪两个值。
  - 还对不上（不是 JSON、值不在表里、缺字段）：请模型改一次（`callStructuredWithFix`）：回放它的原话，再告诉它哪个字段错了、它给的是什么、允许的取值（「verdict：你给的是 "maybe"，只能是 "achieved"、"not_achieved" 之一」），判断不用改、只改格式。
  - 改了还不对：记没办成，原因「复核没做成（复核模型返回的格式不对），结果没有核实，可以人工改结果。」；`sessions.review` 写 `error`（两次哪里不对）和 `rawOutput`（模型最后一次原样返回的文字，截前 2000 字，`RAW_OUTPUT_MAX`），两次的用量都算（格式不对的那次服务没返回花费，按单价估）。已经问过两次，不再整个重试复核。过程记录「AI 复核没做成（模型返回的格式不对），结果记没办成（没有核实）」，详情里有原话。运行详情的复核报告展开多一行「模型原话」。不加新的结果状态（仍是两种），由负责人看了原话决定要不要改结果。
  - 三方验收（`verify.ts`）同样：每条和总结论的 `pass` / `fail` / `unsure` 宽松认（「通过 / 不通过 / 存疑」等，`VERIFY_VERDICT_SYNONYMS`），格式不对请模型改一次；还不对按「验收模型出错」交给负责人（验收争议，原来就这样），另记一条出错的过程记录「三方验收模型返回的格式不对，没能核对」，详情里有原话，用量算进运行。
- **输入按模型的上下文截**（2026-10-30，`log-text.ts` 的 `evidencePromptMax`）：复核、三方验收的输入原来固定最多 8 万字。现在按所用模型的 `context_k` 算：(上下文 − 输出留 8000 token − 系统提示 − 每张截图 2000 token) ÷ 每字 1.2 token，不超过 8 万字、不少于 4000 字；`context_k = 0`（不知道）按 128K 算。每字 1.2 token 是偏保守的估法：中文一个字在各家分词器里大约 0.6～1.1 token，英文、JSON、网址、id 一个字符 0.25～0.4 token，复核材料是中文说明 + JSON + 网页文字混排，平均多在 0.6～0.9。12.8 万以上的模型还是 8 万字；6.4 万的约 4.3 万字；3.2 万的约 1.7 万字。截的方法不变（留开头 6 成、结尾 4 成，连省略标记不超过上限）。

### 5.3 时机和花费

- 在收尾的事务**之后**跑（不占着事务等模型）：先把状态写成「已结束」、结果先空着、写复核标记（`review.pending`，页面显示「复核中」），复核回来再写结果。被派的运行要等复核完再结算派活单、叫醒派活方（见 6.2）。
- worker 中途没了、复核一直没回来：清扫（`work.sweep`，每分钟）发现复核标记超过 10 分钟，清掉标记、结果记没办成（「复核没做成（10 分钟没有结果，worker 可能中途重启了），结果没有核实，可以人工改结果。」，复核期间人已经改过结果的不动），通知负责人，再结算被派的单。
- 花费：文字加一张截图，输入大约 5–15k token。按 deepseek-v4.1-flash 的价格（每百万 token 输入 0.0376 美元、输出 0.08 美元），每次不到 0.001 美元。用量记到这次运行的 token 和花费里。

### 5.4 任务设置

任务的「完成」区块里有「复核模型」（必填，新任务和没选过的旧任务先填上设置里的默认复核模型）。2026-10-20 简化以前还有开关「结束后让 AI 复核」，已经去掉。配了三方验收的任务照样要选复核模型：验收通过的不复核，其余（比如规则没触发验收）照样复核。

### 6.2 单的结果

| 运行的结果 | 单的状态 | 单的结果 | 重试 |
|---|---|---|---|
| 办成 | 办完 | 办成 | — |
| 没办成（agent 报的含只拿到一部分、规则判的、复核判的、复核没能确认的） | 没办成（`not_done` / `missing_result`） | 没办成 | 不重试 |
| 运行出错 | 照现在：还有重试次数就排队重试，没有就没办成（`error`） | 没办成 | 照现在 |
| 人取消、人选不继续、人判验收失败 | 没办成（`cancelled_run`） | 没办成 | 不重试（清扫补写时按 `outcome_by = human` 认） |
| 开不了运行（例如任务没设复核模型） | 没办成（`error`） | 没办成，原因「没能开始运行：…」 | 不重试 |

- 2026-10-20 简化以前还有「没核实 → 办完」「部分办成 → 没办成（`partial`）」两行；迁移 0026 把这些旧单的结果改成没办成，单的状态不改。
- 派活页：列表加「结果」列；状态筛选「在办 / 办完 / 没办成」不变，另外加结果筛选（办成 / 没办成）。2026-10-20 改成三个标签「没结束 / 办成 / 没办成」，去掉结果下拉（见 dispatch.md 第 9.2 节）。
- `work.done` 叫醒派活方时、`work.list` 的每一行，都带上 `outcome` 和 `outcomeReason`。派活方的提示词里写：「每张单有结果（办成 / 没办成）和原因：拿到没办成的单，看原因（缺了什么）自己判断要不要重派或者报给人」。

- 单测：硬规则（agent × 检查点 × 必交结果 × 验收，所有组合都过一遍）和复核结论（办成 / 没办成 / 旧的部分办成、说不准 / 出错）；`run.finish` 校验（not_achieved 没写 reason 要报错，旧的 partial 当没办成）；只回文字时提醒一次，再回文字交给复核；复核出错重试一次；没有复核模型不开始运行；迁移 0024 + 0026 补数据的每一行。
