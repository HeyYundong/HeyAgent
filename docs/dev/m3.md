# M3：规则、检查点、三方验收（开发说明）

## 先读

- `docs/dev/conventions.md`：特别是第 0 节：平台通用，规则和检查点都是通用机制，不写业务。
- `docs/v1-plan.md`：2.3.2（规则）、2.3.3（检查点）、2.3.4（三方验收）、2.3.5（上下文压缩）。
- `docs/dev/api.md`。
- `apps/server/src/engine/hooks.ts`：4 个阶段的钩子，M1 已经留好。
- 原型 `design/prototype/src/mock/shared.ts` 的规则、检查点、`Verification` 类型；原型规则页、任务页的交互。

## 目标

1. 规则用一句话写，**由程序执行**，模型绕不过。
2. 检查点自动记录，agent 自己打勾。
3. 说做完了由另一家的模型逐条核对；有疑问就反问执行的 agent；还说不清就交给负责人。
4. 长 session 自动压缩上下文。
5. agent 自己探索出的步骤，可以一键存成任务步骤。

规则仍然是**每个任务自己选**：没有全局生效的规则，也没有保底规则（原型 v3 已定）。

## 1. 规则：保存时翻译，运行时照翻译结果执行

**翻译**
- 保存规则时，用「规划」默认模型把「触发条件 + 命中后怎么办」翻译成结构化结果，用 zod schema 约束输出。
- 规则页显示「系统理解为：调用 xxx 之前，拦下交给任务负责人审批」，人确认后才生效。

**触发类型**（v1 只支持这几种）

| 类型 | 参数 |
|---|---|
| `before_tool` | 工具 id 列表，或按风险等级：外发、涉及金钱 |
| `after_tool` | 工具 id 列表，或「任意工具」 |
| `url_not_allowed` | 域名白名单 |
| `page_needs_human` | M2 检测到验证码或登录页时，引擎发出的内部信号 |
| `cost_over` | 美元 |
| `agent_done` | — |
| `agent_proposes` | 记忆或技能 |

**动作**

| 动作 | 做什么 |
|---|---|
| `deny` | 拦下，告诉 agent 理由 |
| `ask_human` | 挂起，交给某人审批。给谁：任务负责人、指定的人或主管 |
| `screenshot` | 截图存证 |
| `notify` | 通知某人 |
| `sync_checkpoint` | 自动记录检查点 |
| `verify` | 交给三方验收 |

**翻译不进去**：规则保存为「未生效（v1 还不支持）」，建任务时选不了。**绝不偷偷变成让模型自己判断。**

**执行**
- 引擎在 4 个阶段按 session 快照里的规则执行。
- `hooks.ts` 的「调工具前」要新增一种决定：`ask_human`，含义是挂起等审批。
  - 新建一件「要人办的事」（类型 approval），附上工具名和参数，参数里的密钥要隐藏；
  - session 进入「等人处理」，这次工具调用先存着，还没执行；
  - **批准**：执行这次调用，接着跑；
  - **拒绝**：把「被拒绝：理由」作为工具结果交给 agent，接着跑。
- 每次命中都写一条 `rule` 类型的事件：哪条规则、做了什么。

## 2. 检查点

- **保存任务时**认出每条检查点的类型和目标数（shared 的 `recognizeCheckpoints`），存进库里。
- **自动记录**：任务选了带 `sync_checkpoint` 动作的规则时，调完工具按工具的类别自动写记录，标「自动」，agent 改不了：

  | 检查点类型 | 什么时候记录 |
  |---|---|
  | 访问 | 浏览器打开网页后，记网址和页面标题 |
  | 发送消息 | 调了风险等级为「外发」的工具后，记发给谁和原文 |
  | 产出文件 | 存文件之后，记文件链接 |
  | 数量 | 按记录条数累计 |

  一条记录对应哪个检查点：按类型匹配，同类型有多个时，由 agent 在 `checkpoint.mark` 里指定。
- **agent 自己打勾**：`checkpoint.mark`，标跳过必须写理由（M1 已有）。

## 3. 三方验收

- **什么时候验收**：任务选了带 `verify` 动作、`agent_done` 触发的规则时，agent 说做完了就交给验收。没选这种规则的，说做完了就直接完成。
- **验收模型**：任务自己选的验收模型，或者默认验收模型。**必须和执行模型不是同一家**，建任务时已经检查过；运行时再查一次，同一家就直接失败并写清原因。
- **验收的输入**：
  - 目标；
  - 每条检查点：状态、记录、跳过理由；
  - 最终答复；
  - 证据：产物内容的摘录；截图在验收模型能看图时作为图片传给它。
- **验收的输出**（结构化）：每条检查点给出「通过 / 不通过 / 存疑」和理由，再给一个总结论。存进 `sessions.verification`。
- **有不通过或存疑时**：用 `FinishDecision.continue` 把问题清单交给执行的 agent，问它「为什么」，它可以补做。最多 `verify.maxRounds` 轮（设置项，默认 2）。
- **还说不清**：生成一件「验收争议」（类型 verify）给负责人，附验收报告。负责人有三种处理：
  - 「算通过」：标「已完成」；
  - 「算失败」：标「失败」；
  - 「补充说明后继续」：带着说明回到同一个 session 接着干。
- session 在验收中的状态是「验收中」。

## 4. 记忆和技能的提议

- agent 调 `memory.propose`、`skill.propose` 之后，生成一件要人办的事：类型 memory 或 skill，给任务负责人，主管也能处理。
- 去「待办 → 等人处理」能看到，点进去跳到记忆页或技能页审核。审核功能 M1 已经做了。

## 5. 长 session 压缩上下文

- 发给模型的历史接近上限时，把较早的大块工具输出换成摘要加文件引用：上限是模型上下文的 60%，或者设置里的 token 数。
- 检查点、关键结论、人的回复保留原文。
- 库里保留完整历史，只在消息上标记「已压缩」。
- 每次压缩写一条事件。

## 6. 探索出的步骤

- 新增内置工具 `plan.set({ steps })`，每个任务都自带：agent 开始时写下它打算怎么做，中途可以更新。写成 `plan` 类型的事件。
- session 过程里显示 agent 的步骤，负责人或主管可以点「存为任务步骤」，覆盖到任务的步骤里，记审计。

## 7. 前端

- **规则编辑**：保存时显示「系统理解为……」，确认后生效；未生效的规则标出来，并说明原因。
- **session 过程**：
  - 规则命中的事件；
  - 验收结果：每条检查点的结论和理由；
  - agent 的步骤和「存为任务步骤」。
- **要人办的事**：
  - 「审批工具调用」：显示工具名和参数，可以批准或拒绝，加备注；
  - 「验收争议」：显示验收报告，三种处理方式。
- **新建任务**：选规则时，未生效的规则不能选。

## 分包

| 包 | 内容 | 什么时候 | 在哪 | 库 / 端口 |
|---|---|---|---|---|
| **M3-A 后端** | 第 1～6 条的全部后端，外加给前端的接口：`rules.compile`、规则确认、`tasks.saveStepsFromSession`、处理「审批工具调用」和「验收争议」这两类事等。在 `docs/dev/api.md` 里补全这些接口 | 现在，和 M2-B（浏览器前端）同时 | worktree | `heyagent_m3a` / `heyagent_m3a_test`，API 3106 |
| **M3-B 前端** | 第 7 条 | M3-A、M2-B 合并之后 | 主目录 | 另定 |

M3-A 只改 `apps/server/**`、`packages/shared/**`、`docs/dev/api.md`，**不改 `apps/web`**。M2-B 同时在改前端。

**M2 留下、M3-A 要处理的几件事**：
- **说做完了的先后顺序**：
  - 现在引擎先把 session 标「已完成」，然后在 `finally` 里关工具和 Chrome（`gateway.close()`），过程记录比完成状态晚写。
  - 加验收时把顺序理顺：先验收；最终结论确定后，先关资源、写好过程记录，再写最终状态。
  - 同时修掉 M1 测试里「session 已完成，事件还没写」这类读早了的问题。
- **验证码和登录页**：浏览器检测到时，M2 已经内置「截图 + 生成登录类要人办的事 + 等人」，因为不处理也没法继续。`page_needs_human` 触发的规则只能在这之外**再加**动作（例如通知别人），不能关掉内置的转人工。
- **端到端在开发机上跑**：用本机的 API 和 worker，规则和验收用不到浏览器。不要动 8080 的 pod，那个归 M2-B 用。

## 验收

- 自动化测试用假模型覆盖：
  - 翻译：支持的、不支持的；
  - 规则的 4 个阶段：拦下、审批（批准后执行、拒绝后告诉 agent）；
  - 检查点自动记录；
  - 验收：通过、反问后补做通过、仍有争议交给人；
  - 验收模型和执行模型同一家时失败；
  - 压缩；
  - 存为任务步骤。
- M3-A 在开发机上用真模型跑通一个配置了审批规则 + 验收规则的任务，执行用 Haiku，验收用 Gemini Flash，最多 3 美元。M3-B 再在 pod 上用界面跑一遍。
