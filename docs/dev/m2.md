## 目标

浏览器是平台的通用能力：
- agent 用服务器上**有界面的 Chrome**（跑在 Xvfb 里）操作任何网站；
- 登录态加密存在保险箱里；
- 代理按 Chrome 配置走；
- 并发按「平台 × 账号」限制；
- 遇到验证码或登录页就挂起，人在控制台的远程画面里处理完，回到原来的 session；
- 人也可以在控制台里打开 Chrome，手动登录并保存登录状态。

## 关键设计（两个包都按这个来）

### 1. 任务怎么用浏览器

- **系统自带一个工具「浏览器」**（id `browser`，来源 `builtin`）。任务选了它，就开放整组浏览器工具：
  - Chrome 配置由系统分配（2026-10-19 改）：第一次调浏览器工具时，从本任务允许的里按顺序（position、创建时间）挑一个空闲的。每个 Chrome 同一时间只给一个运行用（`browser/instance.ts` 登记时锁配置行再数）；都被占着就挂起等 `browser.profile:any`，有一个空出来按挂起的先后叫醒（`browser/leases.ts` 的 `wakeProfileWaiters`）。**一次运行从头到尾只用一个 Chrome**：分到的记在 `sessions.browser_profile_id`，挂起再继续时它被占着就等 `browser.profile:<id>`，不换。
  - `browser.use({ profileId })`：可选，只能在还没分到 Chrome 时调（任务要求用某个特定 Chrome 时），被占着就等它；分到以后再调同一个回「已经在用」，调别的报错。
  - Playwright MCP（0.0.83）的工具，名字统一加 `browser.` 前缀。
    - 必须屏蔽 `browser_run_code_unsafe`；
    - `browser_evaluate` 默认不开，任务设置里可以打开；
    - 其余默认全开。
  - `browser.batch`（连着做几步，2026-10-23 加，见 `browser-speed.md`）：一次给 1～20 个动作，网关展开、每一步走一次普通调用，哪一步出错就停，最后附页面概况和快照。会改页面的动作做完，输出末尾附页面概况（标题网址、弹窗和按钮、文件选择框的中文提示）；被「我知道了」这类无害弹窗挡住时系统点掉再做一次。
- **任务上新增两项配置**：
  - 允许用哪些 Chrome 配置：`tasks.browser_profile_ids`；
  - 网址白名单：`tasks.allowed_domains`，不填就是不限制。
  - 两项都进 session 快照。
- **Chrome 懒启动**：第一次真正调浏览器工具时才起，session 结束或挂起时关掉。验证码等人那种挂起例外，见第 5 条。
- **系统提示里加浏览器用法**：先用 `depth` 4～6 看结构，再用 `target` 展开局部，或者用查找工具定位；不要拿全量快照（实测长页面有 73 万字符）。截图默认只存档，不回传给模型。

### 2. 起 Chrome

照 `m0-browser-spike.md` 推荐的启动参数和容器参数。
- 每个 Chrome 配一个独立的 Xvfb；CDP 只绑 127.0.0.1。
- 编排器自己连一条 CDP（`connectOverCDP(ws, { noDefaults: true })`）：
  - 新开一个标签页，关掉启动时的那个（去掉提示条，页面就不会矮 56 像素）；
  - 每个页面都挂弹框监听，但不自动处理，留给 agent 或人；
  - 用 `setStorageState` 装入登录态。
- Playwright MCP 用 stdio 起，带 `--cdp-endpoint`，连同一个 Chrome。
- 关的时候按进程组杀掉 Chrome 和 Xvfb，删掉临时目录。
- 关掉 Chrome 的后台网络请求，免得白白走代理流量（实测会连十几个 Google 地址）。
- 每个 worker 同时最多开几个 Chrome，由设置 `browser.maxPerWorker` 决定，默认 4。满了就排队，session 显示「等待浏览器」。

### 3. 代理

- Chrome 配置里的代理：
  - 带用户名密码的 SOCKS5：每个 Chrome 配置常驻一个 gost 本地转发，用配置文件（权限 0600）启动，密码不写在命令行上；
  - 不带认证的代理，或者 HTTP 代理：直接传给 Chrome；
  - 直连。
- 代理挂了就报错、告警，**绝不退回直连**。
- 加上防 DNS、防 WebRTC 泄漏的参数。

### 4. 登录态保险箱和并发

- **保险箱**：每个 Chrome 配置一份加密的 storageState（cookie + localStorage，配置里可以选择加上 IndexedDB），带版本号。
  - 写回时做三方合并，见 `spikes/browser/lib`，再用版本号 CAS，冲突就重试。
  - 写回前先打开账号的「登录探测网址」，确认还在登录状态。判断方法是通用的：最终地址不像登录页，页面上也没有密码输入框。没配探测网址就跳过这一步。
  - 探测失败就不写回，把账号标成「需要人工」。
- **并发**：按「平台 × 账号」租约（`account_leases`）。
  - 平台新增 `domains` 字段（`platforms.domains`），session 第一次打开某个平台域名下的网址时，用这个 Chrome 配置在该平台的账号去申请租约。
  - 租约满了：先拦下这次导航，session 挂起「等待浏览器」（写回、关 Chrome）；有人释放租约时，叫醒最早的那个。
  - 账号的并发上限在浏览器页里配，默认 1。
  - session 结束、挂起、失败时释放租约。租约带心跳和过期时间，防止 worker 死掉后一直占着。

### 5. 验证码和登录页

- **每次调完浏览器工具都检测**：编排器看当前页面的地址、iframe 域名、标题和正文关键词，规则见调研报告：reCAPTCHA、hCaptcha、Arkose、GeeTest、「验证」「滑块」「Robot Check」「captcha」、登录页特征。
- **拿不准时**，由设置 `browser.visionCheck` 打开（默认关）：把截图交给视觉模型（设置 `browser.visionModel`，默认 `openrouter/qwen/qwen3.8-flash`，只能选能看图的聊天模型）判断「是不是验证码页或登录页」，输出 JSON。
- **验证码先自己试着过**（2026-10-19 用户改的决定，设置 `browser.captchaSolve`，默认开，所有网站都一样；代码在 `apps/server/src/browser/captcha.ts`）：
  - 在页面和各个 frame 里给小图、输入框、按钮、勾选框编号，截页面图和验证码小图的放大图，连同编号列表交给 `browser.visionModel`，只回 JSON：`text`（图里的字符填进哪个框、点哪个按钮提交）/ `click`（「我不是机器人」这类点一下的）/ `other`（滑块、拼图、短信码等，不试）。
  - 检测到验证码页：填好就提交，再按规则（原来是视觉模型认出的，规则拿不准时再问一次视觉模型）看还是不是验证码页；每个页面（主机名 + 路径）最多试 3 次，过不了照下面交给人，卡片上写试过什么。页面上不止一个空着的输入框（验证码是表单里的一项）就不提交，告诉 agent 先填别的、再调 `browser.fill_captcha`（只填不提交）。
  - 登录小 agent 多一个 `login_fill_captcha`（只填不提交）；登录中检测到验证码页也先试着过，一次登录合计最多 3 次。
  - 开关关着时，agent 没有 `browser.fill_captcha`，登录小 agent 也没有 `login_fill_captcha`。
  - 第三方人机验证（规则按 frame 地址认出的 reCAPTCHA、hCaptcha、Turnstile、GeeTest、Arkose 等，`judgePage` 的结果带 `provider`）不自己试、不问模型，直接交给人，卡片和工具输出写「… 是第三方人机验证，系统不自己试」。
  - 每试一次记一条过程「自动过验证码（第 n 次）」（答案、花费），花费和 token 算进这次运行；操作历史记一行 `Captcha`。
- **命中就**：
  1. 截图存成文件；
  2. 生成一件要人办的事，类型 `login`，给任务负责人，标题写清哪个账号、哪个网址，附远程画面入口；
  3. session 进入「等人处理」。
- **Chrome 先保留不关**，最多保留 `browser.humanHoldMinutes` 分钟（默认 30），人在远程画面里处理。
  - 人点「已处理好了」：同一个 Chrome，同一个 session，接着跑；
  - 过了保留时间还没处理：写回、关掉 Chrome，session 继续等人；人处理时再新起一个 Chrome。
- 原来是「只检测，不做任何自动破解」，2026-10-19 用户改成上面的「先自己试着过简单的，过不了再交给人」（很多内部系统要 agent 帮忙过简单的验证码）。

### 6. 网址白名单

任务设了白名单时：
- 调工具前检查导航参数；
- 编排器在浏览器层拦截不在名单里的页面请求（只管主文档）；
- 拦下时把原因告诉 agent。

### 7. 文件

- **上传**：agent 要往网页里传 session 里的文件（例如以图搜同款），用文件 id 指定。网关把文件放进 MCP 能读到的临时目录，再把参数换成路径。
- **截图**：截下来存成 session 文件（类型 screenshot），作为证据（M3 的验收会用到）。
- **下载**（2026-10-19 加，`browser/downloads.ts`）：运行的 Chrome 起来后，编排器开一条浏览器级 CDP 会话，`Browser.setDownloadBehavior({ behavior: "allowAndName", downloadPath: <这个 Chrome 的临时目录>/downloads, eventsEnabled: true })`，听 `Browser.downloadWillBegin` / `downloadProgress`；下完按 `suggestedFilename` 存成 session 文件（类型 download，不限大小）、记一条过程记录，下一次浏览器工具的输出里告诉 agent（`tools.ts` 里一行 `instance.downloads.collect(name)`；点击这类动作调完先等 0.6 秒看有没有下载开始，已经开始的最多等 20 秒下完，再长的在后台下完、下次再说）。实测（worker 镜像的 Chrome）：`<a download>`、新标签页里打开的附件（标签页自己关掉）、blob: 生成的文件、一次点出两个下载都能接住，不弹「另存为」和「要下载多个文件吗」；编排器和 Playwright MCP 都用 `noDefaults` 连 Chrome，不会再设下载行为，所以不会互相覆盖，MCP 自己也收不到下载事件（它的输出里不会有下载）。人在远程画面里点的下载也算。人「打开 Chrome」（登录用的）不接管。选了「浏览器」的任务自动带上「读附件」。
- **Excel**：「读附件」「存文件」支持 xlsx / xls 等表格，见 `files/sheets.ts`（SheetJS，依赖说明见 conventions.md）。

### 8. 远程画面（人看、人操作）

- **worker 为每个开着的 Chrome 提供一个内部 WebSocket**，只绑 127.0.0.1，API 和 worker 在同一个 pod 里，所以 API 能连到。
- **API 提供 `GET /api/browser/view/:browserId`**（WebSocket 升级，要求登录），把两边的数据转过去：
  - 看：任何登录用户都能看；
  - 操作（鼠标、键盘、导航）：只有这个 session 的负责人或被分配的人、主管能做；没权限的连接，输入一律丢弃。
- **消息格式**沿用 `spikes/browser/viewer` 的写法：
  - 服务端 → 浏览器：
    - 二进制消息 = 一帧 JPEG；
    - JSON `{ t: "meta", width, height, tabs: [{ id, title, url, active }], url }`；
    - JSON `{ t: "dialog", kind, message, defaultValue? }`；
    - JSON `{ t: "closed", reason }`。
  - 浏览器 → 服务端（JSON）：
    - `{ t: "mouse", type, x, y, button, buttons, clickCount, modifiers, deltaX, deltaY }`；
    - `{ t: "key", type, key, code, keyCode, text, modifiers }`；
    - `{ t: "text", text }`：中文输入法组好的字、粘贴，服务端用 `Input.insertText`；
    - `{ t: "nav", action: "back" | "forward" | "reload" | "goto", url? }`：goto 也受白名单限制；
    - `{ t: "tab", id }`；
    - `{ t: "closeTab", id }`；
    - `{ t: "dialog", accept, promptText? }`。
- **帧率和流量**：画面缩到 960 宽；收到帧立刻确认；慢的观看端靠丢帧应对；只在有人看的时候开 screencast（实测每路 6～12Mbps、约 1 核）。
- **人手动登录**：浏览器页「打开 Chrome 登录」。
  - 起一个不挂 session 的 Chrome，装上这个配置的登录态，打开账号的探测网址或平台首页；
  - 人点「保存登录状态」：整份导出，替换保险箱内容，版本号加一（CAS）；
  - 点「关闭」：不保存。
  - 这类 Chrome 空闲 30 分钟自动关闭。

### 9. 接口

新建 `apps/server/src/trpc/browser-router.ts`，挂在 `appRouter.browser` 下，监工会先挂好：
- `openForLogin({ profileId, accountId? })` → `{ browserId }`
- `saveLogin({ browserId })`
- `close({ browserId })`
- `live()`：现在开着的 Chrome：哪个配置、哪个 session、谁在看
- `sessionBrowser({ sessionId })`：这个 session 现在有没有开着的 Chrome，有就返回 browserId
- `accountStatus()`：各「平台 × 账号」的使用数 / 上限、状态

## 验收

- typecheck、lint、build、test 全过。
- 浏览器相关的测试在 worker 镜像的容器里跑，因为要有界面的 Chrome 和 Xvfb。测试站点用本地起的页面，覆盖：
  - 登录、cookie 轮换；
  - 合并写回（两个 session 交替）；
  - 探测失败不写回；
  - 租约排队和释放；
  - 验证码页检测 → 等人 → 处理完继续同一个 Chrome；
  - 白名单拦截；
  - 文件上传；
  - gost 带认证的上游（本地测试 SOCKS5 服务器）；
  - 远程画面：帧、输入、中文、权限（没权限的输入被丢弃）。
- M2-A：在 8080 的 pod 上用真模型（Haiku），通过接口（tRPC 和 curl，不用界面）跑通下面两件事。M2-B 用界面再跑一遍：
  1. 建一个任务：打开 https://example.com，读出页面标题，用存文件工具保存，选「浏览器」工具 → 完成，产物正确，过程里有截图。
  2. 本地验证码测试页 → session 等人 → 在控制台远程画面里点「已处理好了」→ 继续。
- 真模型花费写进汇报，M2 最多 3 美元。
- 验收完，pod 恢复成空白环境。
